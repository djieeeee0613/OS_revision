    1.1 作業系統在做什麼 (What Operating Systems Do)

    為什麼需要 OS

    桌機、筆電、平板、手機的硬體各不相同（CPU、記憶體、硬碟、各種連接埠…）。如果沒有 OS，每個應用程式都得自己去控制這些硬體。OS 把硬體包起來，提供一致、方便的使用環境。

    電腦系統的四個組成（由上到下）

            user（使用者）
          ↕
  application programs（應用程式：編譯器、瀏覽器、開發工具…）
          ↕
  operating system（作業系統）
          ↕
  computer hardware（硬體：CPU、memory、I/O devices…）

    Shell（殼層）＝ Command Interpreter（命令直譯器）

    • 工作：取得並執行使用者下的下一個命令（get and execute the next user-specified command）。
    • 兩種形式：
      • GUI（Graphical User Interface，圖形使用者介面）
      • CLI（Command Line Interface，命令列介面）
    • 層次關係：Applications → Shell → Operating System → Hardware（一層包一層）。

    投影片例子：macOS 的 Finder 視窗、iPad 的主畫面是 GUI；Windows 的「命令提示字元」黑底視窗是 CLI。 補充例子：在 Linux Terminal 輸入 ls 列出檔案，bash 就是一種 shell。

    OS 的定義

    Operating System（作業系統）：

    • 管理電腦硬體的軟體。
    • 作為使用者與硬體之間的intermediary（中介者）。
    • 目的：提供一個環境，讓使用者能以 convenient（方便） 且 efficient（有效率） 的方式執行程式。

    OS 的兩種角色：

    角色 中文 說明
    Resource allocator 資源分配者 管理所有資源；當多個請求互相衝突時，決定如何分配才有效率又公平
    Control program 控制程式 管理使用者程式的執行，防止錯誤與不當使用電腦

    補充例子：OS 像餐廳經理。桌位、廚師、食材是資源（resource allocator 負責分配）；客人不能自己闖進廚房動刀動火（control program 負責管制）。

    沒有全世界公認的定義，常見兩種說法：

    1. 簡單觀點：廠商賣 OS 時附帶的所有東西都算（但各家差異很大）。
    2. 較常見的定義：OS 是電腦上隨時都在執行的那一個程式，通常稱為 kernel（核心）。

    除了 kernel 之外還有兩類程式：

    類別 中文 說明
    System programs 系統程式 和 OS 有關，但不一定是 kernel 的一部分
    Application programs 應用程式 和系統運作無關的所有程式

    現代 OS（通用與行動裝置）包含三部分：

    1. 一直在執行的 kernel
    2. Middleware frameworks（中介軟體框架）：讓應用程式開發更容易，並提供資料庫、多媒體、繪圖等功能
    3. 系統執行期間協助管理的 system programs

    投影片例子：Android 架構由下到上為 hardware → Linux kernel → Bionic（C 函式庫）/ HAL（硬體抽象層）→ native libraries（SQLite、openGL、webkit、SSL、media framework、surface manager）→ ART VM、Android frameworks、JNI → applications。其中 SQLite、openGL 這些就是 middleware。

    OS 提供的服務（A View of OS Services）

    • 最上層：user and other system programs
    • User interfaces：GUI、touch screen（觸控螢幕）、command line
    • System calls（系統呼叫）：程式進入 OS 的入口
    • Kernel 內的服務：
    服務 中文
    program execution 程式執行
    I/O operations 輸入輸出操作
    file systems 檔案系統
    communication 通訊
    resource allocation 資源分配
    accounting 使用紀錄／記帳
    error detection 錯誤偵測
    protection and security 保護與安全

    一句話總結：OS 做四件事

    Management（管理）、Allocation（分配）、Control（控制）、Service（服務）

    1.2 電腦系統組織 (Computer-System Organization)

    基本架構

    現代電腦由一或多個 CPU 與多個 device controller（裝置控制器） 組成，透過共用的 bus（匯流排） 連接，並共同存取 shared memory（共享記憶體）。

     disks      mouse keyboard printer    monitor
   |           \     |     /             |
[CPU]  [disk controller]  [USB controller]  [graphics adapter]
  |          |                  |                  |
  +----------+--------bus-------+------------------+
                      |
                   [memory]

    開機流程（Computer Startup）— OS 執行時機 (1)

    電腦一開機需要一個起始程式：bootstrap program（啟動程式／靴帶程式）。

    • 通常存在 ROM、EEPROM 或 flash 記憶體中（統稱 firmware，韌體）。
    • 工作：
      1. 初始化系統各部分（CPU 暫存器、裝置控制器、記憶體內容…）
      2. 把 OS kernel 從磁碟載入到 RAM
      3. 開始執行 OS
    • OS 啟動後執行第一個 process（例如 init），然後等待事件發生。

    投影片圖示的三步驟：

    1. CPU 先執行 ROM 裡的 bootstrap program
    2. bootstrap 到磁碟找到 kernel image（核心映像檔）
    3. 把 kernel image 載入 RAM，之後 GUI / Shell 也被載入記憶體

    補充例子：按下電源鍵後看到主機板 logo 的那段時間，就是 firmware 裡的 bootstrap 在跑；看到 Windows / Ubuntu 登入畫面時，kernel 已載入完成，GUI shell 也啟動了。

    中斷 (Interrupt) — OS 執行時機 (2)

    Interrupt（中斷）：通知 CPU「有事件需要處理」的機制。OS 是 interrupt-driven（中斷驅動）的。

    兩種觸發來源：

    來源 方式 例子
    H/W（硬體） 送出硬體訊號給 CPU 鍵盤按鍵、磁碟讀完資料、計時器到時
    S/W（軟體） 執行 system call（也叫 monitor call） 程式要求讀檔

    中斷處理流程：

    1. CPU 收到中斷，暫停目前工作。
    2. 中斷架構必須保存被中斷指令的位址，之後才能回來繼續執行。
    3. 透過 interrupt vector（中斷向量） 找到對應的處理程式。
      • interrupt vector 是一張表，存放所有服務程式的位址。
    4. 把控制權轉給 ISR（Interrupt Service Routine，中斷服務常式）。
    5. ISR 處理完，回到原本被中斷的程式。

    Windows 與 UNIX 都採用這種做法。記憶體中相關的 OS 元件：interrupt vector、ISRs、device drivers。

    Instruction cycle with interrupts（含中斷的指令週期）：CPU 每執行完一道指令，就檢查有沒有中斷；有的話就去處理。

    補充例子：你在寫作業（執行使用者程式），手機響了（interrupt）。你在書上夾書籤（保存位址），查通訊錄看是誰打來、該怎麼應對（查 interrupt vector），接電話（執行 ISR），講完翻回書籤那頁繼續寫（return）。

    Interrupt Timeline（單一程式做輸出的時間軸）

    • CPU 平時在執行 user program；I/O device 平時 idle（閒置）。
    • 發出 I/O request → 裝置開始 transferring（傳輸）→ transfer done → interrupt signaled（發出中斷）→ CPU 切去做 I/O interrupt processing → interrupt handled → CPU 回到 user program。

    Interrupt-driven I/O Cycle（中斷驅動 I/O 循環）7 步驟

    步驟 誰 動作
    1 CPU device driver 啟動 I/O
    2 I/O controller 開始 I/O
    3 I/O controller 輸入備妥／輸出完成／發生錯誤 → 產生中斷訊號
    4 CPU 收到中斷，把控制權交給 interrupt handler
    5 CPU interrupt handler 處理資料，從中斷返回
    6 CPU 回復執行被中斷的工作
    7 — 回到步驟 1（CPU 在指令之間持續檢查中斷）

    Intel 處理器事件向量表（Event-vector Table）重點

    向量編號 說明 中文
    0 divide error 除法錯誤（除以零）
    3 breakpoint 中斷點（除錯用）
    6 invalid opcode 無效的運算碼
    11 segment not present 區段不存在
    12 stack fault 堆疊錯誤
    13 general protection 一般保護錯誤
    14 page fault 分頁錯誤
    0–31 — non-maskable（不可遮罩），多為錯誤／例外
    32–255 maskable interrupts 可遮罩中斷，給裝置使用

    I/O 結構 (I/O Structure)

    Device controller（裝置控制器）：

    • 內部有 local buffer（本地緩衝區） 與一組特殊用途暫存器（special-purpose registers）。
    • 負責在它控制的周邊裝置與自己的 local buffer 之間搬資料。

    Device driver（裝置驅動程式）：OS 為每個 device controller 準備一個，是 OS 與控制器溝通的軟體。

    一次 I/O 的流程：

    1. device driver 把適當的值載入控制器的 registers。
    2. 控制器檢查 registers，執行要求的 I/O（如果是 read，就把資料從裝置搬到 local buffer）。
    3. 傳輸完成後，控制器發出 interrupt 通知 CPU。

    兩種 I/O 方式比較重點

    Interrupt-driven I/O（中斷驅動 I/O） DMA I/O（Direct Memory Access，直接記憶體存取）
    CPU 是否介入搬資料 要。CPU 需主動把資料在記憶體與 I/O 模組間搬移 不用。DMA 模組代替 CPU 完成
    硬體需求 無額外硬體 系統匯流排上多一個 DMA 模組
    中斷次數 低速裝置每個 byte 一次中斷 每個 block 只產生一次中斷
    CPU 負擔 CPU 被 I/O 綁住，每次傳輸都要執行許多指令 傳輸期間 CPU 可以去做別的事
    資料路徑 裝置 → 控制器 buffer →（CPU 經 ISR）→ 記憶體 裝置 → 控制器 buffer → 直接到記憶體
    適合 低速裝置（鍵盤、滑鼠） 高速、大量資料（磁碟、網路卡）

    補充例子：

    • Interrupt-driven 像老闆親自搬貨：每到一箱，倉管就叫老闆（中斷）來搬進倉庫，老闆沒辦法做別的事。
    • DMA 像請了搬運工：老闆只說「把這一車搬到 A 區」，搬運工整車搬完後才回報一次，老闆這段時間可以處理其他事。

    現代電腦如何運作（整合圖）

    編號 動作
    1 CPU 與 memory 之間：instruction execution cycle（指令執行週期）
    2 CPU → device：I/O request
    3 CPU ↔ device：data
    4 device ↔ memory：DMA（不經 CPU）
    5 device → CPU：interrupt
    6 CPU ↔ memory：data movement（資料搬移）

    儲存結構 (Storage Structure)

    各種儲存裝置的主要差異：speed（速度）、cost（成本）、size（容量）、volatility（揮發性）。

    • Volatile（揮發性）：斷電後資料消失。
    • Nonvolatile（非揮發性）：斷電後資料仍在。

    Storage-Device Hierarchy（儲存裝置階層，Fig. 1.6）

       容量小 / 速度快 / 貴

  │ registers（暫存器）   │ ┐
  │ cache（快取）         │ ├ primary storage（主儲存）  → volatile
  │ main memory（主記憶體）│ ┘
  ├ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤ ← 揮發 / 非揮發分界
  │ nonvolatile memory    │ ┐ secondary storage（輔助儲存）
  │ hard-disk drives      │ ┘
  │ optical disk（光碟）   │ ┐ tertiary storage（第三級儲存） → nonvolatile
  │ magnetic tapes（磁帶） │ ┘
  └─────────────────────┘
   容量大 / 速度慢 / 便宜

    Caching（快取）：把資訊複製到較快的儲存系統。主記憶體可視為輔助儲存的 cache。（詳見 1.5.5）

    1.3 電腦系統架構 (Computer-System Architecture)

    依通用處理器的數量粗略分三類，不同架構會影響 OS 的設計：

    1. Single-Processor Systems（單處理器系統）
    2. Multiprocessor Systems（多處理器系統）
    3. Clustered Systems（叢集系統）

    Multiprocessor Systems（多處理器系統）

    • 有兩個以上的處理器，共享 bus，有時也共享 clock（時脈）、memory、周邊裝置。
    • 主要優點：increased throughput（提高產能／吞吐量）——單位時間內完成更多工作。
    SMP：Symmetric Multiprocessing（對稱式多處理） Asymmetric Multiprocessing（非對稱式多處理）
    分工 每個 CPU 地位對等（peer），都能執行所有工作，包括 OS 功能與使用者 process 每個處理器被指派特定工作
    特點 多個 process 可同時執行而效能不會明顯下降 一個 boss 處理器負責排程、分派工作給 worker 處理器
    使用情況 大多數系統採用；Windows、macOS、Linux、Android、iOS 都支援 較少見

    補充例子：SMP 像一間每位櫃員都能辦所有業務的銀行；Asymmetric 像有一位主管專門分派工作，其他人只負責被指派的項目。

    Multiple chips vs. Multicore

    • Multicore（多核心）：把多個運算 core（核心） 放在同一顆晶片上。
      • 比多顆單核晶片更省電、更有效率，因為晶片內通訊（on-chip communication）比較快。
      • 對 OS 而言，N 核心的 CPU 看起來就像 N 個標準處理器。
    • 投影片例子：dual-core（雙核心）設計——兩個核心放在同一顆晶片上。

    記憶體存取模型（Memory Access Model）

    模型 中文 說明
    UMA（Uniform Memory Access） 一致記憶體存取 任何 CPU 存取任何 RAM 的時間都相同；SMP 架構採用
    NUMA（Non-Uniform Memory Access） 非一致記憶體存取 CPU 存取某些部分的記憶體比較快（通常是自己本地的記憶體），存取其他部分較慢

    Clustered Systems（叢集系統）

    • 由兩個以上獨立的系統（node，節點） 連結而成。
    • 普遍接受的定義：叢集中的電腦共享儲存裝置，並透過 LAN 或更快的互連（如 InfiniBand）緊密連結。
    • 投影片例子：web cluster、game server cluster、computing cluster；LVS Cluster 架構——Clients 經 Internet/Intranet 連到 Load Balancer（負載平衡器），再由它分派給後端多台 Real Server，對外看起來像一台 Virtual Server。

    用途一：High availability（高可用性）

    • 即使叢集中一台或多台系統故障，服務仍然持續。
    • 提高 reliability（可靠度）。
    • Graceful degradation（優雅降級）：能依照「存活硬體的比例」持續提供服務的能力。
    • Fault-tolerant system（容錯系統）：任何單一元件故障仍能繼續運作。
      • 投影片例子：HP NonStop（前身 Tandem）同時使用硬體與軟體備援。

    補充例子：10 台伺服器壞了 2 台，系統還能提供約 80% 的服務量而不是整個掛掉，這就是 graceful degradation。

    叢集結構

    Asymmetric clustering（非對稱叢集） Symmetric clustering（對稱叢集）
    做法 一台機器處於 hot-standby（熱待機） 模式，只負責監控；另一台執行應用程式 兩台以上主機都在執行應用程式，並互相監控
    故障時 待機那台接手 其他主機分擔
    效率 待機機器平時沒在做事 硬體利用率較高

    用途二：High-performance computing（HPC，高效能運算）

    • 應用程式必須寫成能 parallelization（平行化）。
    • DLM（Distributed Lock Manager，分散式鎖管理器）：提供存取控制與鎖定，避免對共享資料的衝突操作。

    SAN（Storage-Area Network，儲存區域網路）：讓許多系統連接到同一個儲存池（Fig. 1.8）。

    1.4 作業系統的運作 (Operating-System Operations)

    1.4.1 Multiprogramming 與 Multitasking

    三種系統的演進重點

    Single tasking（單工） Multiprogramming（多元程式） Multitasking / Time-sharing（多工／分時）
    記憶體中的程式 一次一個 同時放多個 process 同時放多個 process
    切換時機 不切換 目前的 process 需要等待（如等 I/O）時才切換 時間片用完就切換，非常頻繁
    目標 — 提高 CPU utilization（CPU 使用率） 提供快速的 response time（回應時間）
    問題 單一程式無法讓 CPU 或 I/O 一直忙碌，效率差 有效率，但不保證公平（某程式可能一直佔著 CPU） 需要更多 OS 功能支援

    Multiprogramming：把程式組織起來，讓 CPU 永遠有東西可以執行。

    • Process（行程）：執行中的程式（a program in execution）。
    • 帶來兩個 OS 設計問題：
      • Job scheduling（工作排程）：決定哪些工作載入記憶體。
      • CPU scheduling（CPU 排程）：決定記憶體中哪個 process 下一個使用 CPU。

    Multitasking 是 multiprogramming 的邏輯延伸：CPU 在多個 process 之間切換，切換得非常頻繁，讓使用者感覺反應很快。

    Time-sharing（分時）：

    • 把時間切成一段段 time slice（時間片），每個工作一次只能執行一個時間片。
    • 時間片結束，目前的工作被擱置，換下一個工作。
    • 這樣快速地輪替（shuffling），造成多個工作同時執行的錯覺（illusion）。

    補充例子：

    • Multiprogramming 像廚師煮湯要等 20 分鐘時，先去切菜，不乾等（有等待才換）。
    • Multitasking 像廚師每 10 秒就換一道菜顧一下，每桌客人都覺得自己的菜一直有人在處理。
    • 你邊聽 Spotify、邊用 Chrome、邊開 VS Code，單核心 CPU 其實是輪流做，只是切得太快你感覺不出來。

    Multiprogramming 需要的 OS 功能

    • Memory management（記憶體管理）
    • CPU scheduling（CPU 排程）：從記憶體中已就緒的工作挑下一個執行
    • Concurrency control（並行控制）：多個工作並行時，必須限制它們互相影響的能力（包括排程、磁碟儲存、記憶體管理各階段）
      • 投影片例子：Appl. #1 與 Appl. #2 同時存取同一個檔案。

    Multitasking 額外需要的 OS 功能

    • 確保合理的 response time
    • Virtual memory（虛擬記憶體）：允許執行沒有完全載入記憶體的 process
    • File system and storage management（檔案系統與儲存管理）
    • Protection（保護）
    • Process synchronization and communication（行程同步與通訊）：確保有秩序地執行
    • Deadlock avoidance（死結避免）

    中斷、Trap 與 Exception — OS 執行時機 (3)

    現代 OS 是 interrupt-driven：沒有 process 要執行、沒有 I/O 要服務、沒有使用者要回應時，OS 就安靜地等待事情發生。事件幾乎都是由 interrupt 或 trap 來通知。

    Trap（陷阱）＝ Exception（例外）：軟體產生的中斷，原因有兩種：

    1. 錯誤：如 divide by zero（除以零）、invalid memory access（無效的記憶體存取）
    2. 使用者程式的特定請求：要求 OS 提供服務，也就是 system call

    Exception 處理流程（投影片 投影片：A = 5/0）：

    1. CPU 執行記憶體中的應用程式
    2. 發生錯誤（除以零）
    3. CPU 查 interrupt vector
    4. 跳到 OS 的 exception handler（例外處理常式） 處理（通常是終止該程式）

    Program Misbehavior（程式行為不當）— 四個例子重點

    投影片問：哪一個會造成 exception？

    程式 1：除以零

    #include <stdio.h>
int main() {
    int a;
    a = 5/0;
    printf("a=%d", a);
    return 0;
}

    → 會。觸發 divide error（Intel 向量 0）。投影片實測：編譯時有 division by zero 警告，執行後 Windows 顯示「prog1.exe 已經停止運作」。

    程式 2：寫入空指標附近的位址

    #include <stdio.h>
int main() {
    char *b;
    b = (char *)0;
    b[10] = 'A';
    printf("b[10]=%c", b[10]);
    return 0;
}

    → 會。b 指向位址 0，寫入 b[10] 是 invalid memory access，被 OS 攔下並終止程式。

    程式 3：寫入超出配置範圍的位址

    #include <stdio.h>
#include <malloc.h>
int main() {
    char *b;
    b = (char *)malloc(10);
    b[10000] = 'A';
    printf("b[10000]=%c", b[10000]);
    return 0;
}

    → 投影片實測也被終止。只配置 10 bytes 卻寫到第 10000 個位置，超出範圍。 （補充：這類越界存取是否當掉，要看該位址是否剛好落在這個 process 被允許存取的範圍內；沒當掉不代表程式正確。）

    程式 4：無窮迴圈

    #include <stdio.h>
int main() {
    char *b;
    while (1) {};
    printf("GG");
    return 0;
}

    → 不會產生 exception。程式只是卡住，畫面全黑、永遠印不出 GG。這不是錯誤指令，CPU 無法靠 exception 偵測，必須靠 timer（計時器） 解決（見 1.4.3）。

    結論：設計良好的 OS 必須確保一個不正確或 malicious（惡意） 的程式，不會讓其他程式或 OS 本身執行錯誤。process 可能出的問題有：

    • infinite loop（無窮迴圈）→ 用 Timer 解決
    • 修改其他 process 的記憶體、修改 OS → 用 Dual-mode 與記憶體保護解決

    1.4.2 Dual-Mode 與 Multimode Operation（雙模式與多模式運作）

    目的：必須區分「正在執行 OS 的程式碼」還是「使用者的程式碼」。大多數電腦由硬體提供至少兩種模式，用一個 mode bit（模式位元） 表示目前模式。

    模式 mode bit 別名 代表誰執行
    User mode（使用者模式） 1 — 代表使用者
    Kernel mode（核心模式） 0 supervisor mode（監督模式）、system mode（系統模式）、privileged mode（特權模式） 代表 OS

    模式切換：

                  interrupt / trap / system call
   User mode ─────────────────────────────→ Kernel mode
   (bit = 1) ←───────────────────────────── (bit = 0)
                    set user mode
    • 發生 interrupt（硬體或軟體）或 trap 時，硬體切換到 kernel mode 執行 OS 程式碼。
    • 處理完成後切回 user mode，把控制權還給使用者程式。
    • 作用：保護 OS 不受 errant（出錯的） 使用者影響，也保護使用者彼此不互相干擾。

    Privileged instructions（特權指令）：

    • 可能造成危害的指令，只能在 kernel mode 執行。
    • 例如：切換到 kernel mode 的指令、I/O 控制、timer 管理、interrupt 管理。
    • 如果在 user mode 嘗試執行，硬體視為非法，並 trap 到 OS。

    補充例子：銀行大廳（user mode）的客人不能自己進金庫；要領錢得到櫃檯申請（system call），由行員（kernel mode）進金庫處理。客人硬闖金庫（執行特權指令）會被保全攔下（trap）。

    Multimode（多模式）：

    • Windows、UNIX、Linux 等現代 OS 都利用 dual-mode 來加強保護。
    • 越來越多 CPU 支援超過兩種模式：
      • 支援虛擬化的 CPU 有 VMM（Virtual Machine Manager）mode 給 guest VM 使用。
      • 不同 kernel 元件使用不同模式。
      • 投影片例子：Intel 64 系列 CPU 支援 4 個 privilege level（特權等級），又稱 protection rings（保護環），並支援虛擬化。

    System Call（系統呼叫）— OS 執行時機 (4)

    System call：讓使用者程式請 OS 代為執行 OS 工作的方法。

    • 通常以 trap 的形式跳到 interrupt vector 中的特定位置。
    • 可用通用的 trap 指令，有些系統有專用的 syscall 指令。
    • 執行 system call 時，硬體把它當成 software interrupt（軟體中斷） 處理。

    Transition from User to Kernel Mode（Fig. 1.13）：

    user mode (bit=1)   user process 執行 → 呼叫 system call        從 system call 返回
───────────────────────────│────────────────────────↑──────────
kernel mode (bit=0)       trap (bit=0) → 執行 system call → return (bit=1)

    System call 的執行步驟（How a system call can be made）：

    步驟 動作
    ① User program 發出 system call，trap 進入 kernel
    ② OS 查 dispatch table（分派表）
    ③ 找到並執行對應的 service routine（服務常式）
    ④ 執行完畢，返回 user program

    投影片例子：一個簡單的 shell 程式

    int main() {
    int pid = 1, i;
    char c[100];

    while (scanf("%s", c)) {
        if (strcmp("exit", c) == 0) {
            exit(0);
        } else {
            pid = fork();              // 呼叫 C Library 中的 fork
            if (pid == 0) {            // 子行程
                printf("%s\n", c);
                i = execlp(c, c, NULL);
                if (i == -1)
                    printf("Command Error!!\n");
                printf("Child terminal.\n");
                exit(0);
            } else {                   // 父行程
                printf("Parent had fork a child with PID %d.\n", pid);
            }
        }
    }
}

    說明：程式不斷讀入使用者輸入的命令。輸入 exit 就結束；否則用 fork() 建立子行程，子行程用 execlp() 把自己換成要執行的命令。fork()、execlp()、exit() 都會透過 C 函式庫發出 system call，進入 kernel mode 由 OS 完成。這正是 shell（command interpreter）的基本原理。

    1.4.3 Timer（計時器）

    目的：防止使用者程式霸佔 CPU（例如陷入無窮迴圈），確保 OS 能維持對 CPU 的控制。

    • 設定一個 timer，在指定時間後中斷電腦。
    • 在排程 process 之前先設好，以便之後取回控制權，或終止超過配額時間的程式。
    • 時間長度可以是固定的或可變的。
    • 做法：用允許的執行時間初始化一個 counter（計數器），倒數到 0 就產生中斷。
    • 設定 timer 的指令是 privileged instruction。

    Timer interrupt 處理流程：Appl. #1 在 user mode 執行 → timer 發出中斷 → 切到 kernel mode，經 interrupt vector 找到 timer handler → OS 決定下一個執行誰 → 切回 user mode 執行 Appl. #2。

    補充例子：辯論賽的計時鈴。不管講者講到哪，時間到主持人就打斷換人。前面「程式 4 無窮迴圈」就是靠這個機制，OS 才有機會把 CPU 拿回來分給別的程式。

    1.5.1 Process Management（行程管理）

    Program vs. Process重點

    Program（程式） Process（行程）
    性質 Passive entity（被動實體） Active entity（主動實體）
    存在位置 磁碟上的檔案內容 載入記憶體、正在執行
    定義 指令的集合 A process is a program in execution（執行中的程式）

    補充例子：食譜是 program，照著食譜「正在做菜」這件事是 process。同一份食譜可以同時有兩個人各做一份（同一個程式開兩個視窗 = 兩個 process）。

    • Process 需要資源來完成工作：CPU time、memory、I/O、files、初始化資料。

    Thread（執行緒）：

    Single-threaded process（單執行緒行程） Multi-threaded process（多執行緒行程）
    Program counter（程式計數器） 一個，指向下一道要執行的指令 多個，每個 thread 一個
    • 系統通常有很多 process（有些是 user process，有些是 OS process），在一或多個 CPU 上並行（concurrently） 執行。
    • 並行的實現：讓 CPU 在各 process / thread 之間 multiplexing（多工切換）。

    Process management 的工作：

    • 在 CPU 上排程 process 與 thread
    • 建立與刪除 user / system process
    • 暫停（suspend）與恢復（resume）process
    • 提供 process synchronization（行程同步） 機制
    • 提供 process communication（行程通訊） 機制

    1.5.2 Memory Management（記憶體管理）

    • 為了提高 CPU 使用率與回應速度，要同時把多個程式放在記憶體，因此需要記憶體管理。
    • 選擇記憶體管理方案時必須考慮硬體設計，每種演算法需要各自的硬體支援。
    • 常見方案：
      • Contiguous allocation（連續配置）
      • Segmentation（分段）
      • Paging（分頁）

    Main-memory management 的工作：

    • 追蹤記憶體的哪些部分正在被使用、被誰使用
    • 決定哪些 process（或其部分）與資料要移入、移出記憶體
    • 依需要配置（allocate） 與釋放（deallocate） 記憶體空間

    兩個經典問題：

    問題 中文 說明
    Placement problem 放置問題 新的 process 要放進哪一塊空閒空間？
    Replacement problem 置換問題 記憶體滿了，要把誰換出去？

    投影片例子：記憶體中有 30K、50K、20K、15K 幾塊空位，P1、P2、P3…Pn 等待載入——該把誰放到哪一塊？

    1.5.3 File-System Management（檔案系統管理）

    • OS 對資訊儲存提供一致的、邏輯的觀點（uniform, logical view）。
      • 把儲存裝置的實體特性抽象化，定義出邏輯儲存單位：file（檔案）。
      • 把檔案 mapping（對應） 到實體媒體上，並透過儲存裝置存取。
    • 各種媒體特性不同：存取速度、容量、資料傳輸率、存取方式（sequential 循序 或 random 隨機）。
    • 檔案通常組織成 directories（目錄）。
    • 大多數系統有 access control（存取控制），決定誰能存取什麼。

    重點：使用者看到的是 files 與 directories，而不是底層的 storage blocks（儲存區塊）。

    File management 的工作：

    • 建立與刪除檔案、目錄
    • 提供操作檔案與目錄的 primitives（基本操作）
    • 把檔案對應到 mass storage
    • 把檔案備份到穩定（非揮發性）的儲存媒體

    1.5.4 Mass-Storage Management（大量儲存管理）

    • 現代電腦以 HDD（硬碟） 與 NVM（Non-Volatile Memory，非揮發性記憶體，如 SSD） 作為主要線上儲存媒體，存放程式與資料。
    • 輔助儲存的妥善管理非常重要：整台電腦的運作速度可能取決於（hinge on）輔助儲存子系統及其演算法。
    • 有些儲存不需要快：tertiary storage（第三級儲存），如光碟、磁帶——仍需由 OS 或應用程式管理。

    Secondary storage management 的工作：

    工作 中文
    Mounting / unmounting 掛載／卸載
    Free-space management 可用空間管理（方法：bit-mapping 位元映射、linked list 鏈結串列）
    Storage allocation 儲存空間配置
    Disk scheduling 磁碟排程
    Partitioning 分割
    Protection 保護

    補充例子：插入 USB 隨身碟後系統把它「掛上來」變成 E: 槽（mount）；「安全移除硬體」就是 unmount。

    1.5.5 Caching Management（快取管理）

    Caching 是電腦中很重要的原則，在硬體、OS、軟體各層都會用到。

    原理：

    1. 把使用中的資訊，從較慢的儲存暫時複製到較快的儲存。
    2. 需要資料時先檢查 cache。
    3. 有 → 直接從 cache 使用（快）。
    4. 沒有 → 把資料複製到 cache 再使用。

    補充例子：常用的書放桌上（cache），不常用的放書架（main memory），更少用的放倉庫（disk）。要找書先看桌上，沒有才去書架拿，拿來後順手放桌上。

    存取時間 (ns) 0.25–0.5 0.5–25 80–250 25,000–50,000 5,000,000

    Hardware cache（硬體快取） Software-controlled cache（軟體控制快取）
    控制者 硬體，OS 不介入 OS
    例子 instruction cache、data cache；資料從 cache 到 CPU 與 registers 的傳輸 OS 在主記憶體中維護檔案系統資料的 cache；資料從磁碟到記憶體的傳輸
    設計重點 — Cache management：cache 大小與 replacement policy（置換策略）

    Cache Coherency（快取一致性）

    問題：同一筆資料有多份副本時，如何保持一致？

    環境 情況 處理
    Multiprocessor（多處理器） 每個 CPU 都有自己的 local cache，可能存有同一個變數 A 的值在一個 cache 更新後，必須立刻反映到所有存有 A 的 cache。通常是硬體議題
    Distributed（分散式） 同一檔案的多個 replica（複本） 存在不同電腦 一處更新後，其他複本要盡快更新

    多處理器的簡單解法：共享記憶體改變時，通知其他處理器「你的 cache 副本已經 invalid（失效）」，請它們改回共享記憶體讀取。

    補充例子：兩人各自下載同一份 Google 文件離線編輯，若不同步，雙方手上的內容就不一致。

    Emulation（模擬）

    • 用軟體模擬電腦硬體，通常用在來源 CPU 與目標 CPU 類型不同的情況。
    • 一般是最慢的方法（每道指令都要翻譯）。
    Virtualization Emulation
    CPU 類型 guest 與 host 相同 來源與目標不同
    速度 較快 最慢

    投影片例子：

    • Apple 從 IBM Power CPU 換成 Intel x86 時，Rosetta 模擬器讓為 IBM CPU 編譯的程式能在 Intel CPU 上跑。
    • Android emulator：模擬一般行動裝置的所有軟硬體功能（除了無法真的撥電話），不需實體手機就能開發、測試 Android App。

    虛擬化的用途

    • 筆電／桌機同時跑多個 OS，用來探索或執行為其他 OS 寫的應用程式（投影片 例：Apple 筆電以 macOS 為 host、Windows 為 guest）
    • 不需多台電腦就能為多種 OS 開發、測試、除錯應用程式
    • 在資料中心內執行與管理運算環境

    1.8 分散式系統 (Distributed Systems)

    Distributed system（分散式系統）：一群實體上分開、可能是 heterogeneous（異質的） 的電腦系統，透過網路連結，讓使用者能存取系統所維護的各種資源。

    優點：共享資源可以提高

    • computational speed（運算速度）
    • functionality（功能性）
    • data availability（資料可用性）
    • reliability（可靠度）

    需要的基礎：network protocol（網路協定）、network adapter（網路介面卡）、device driver。

    Network Operating System（網路作業系統） Distributed Operating System（分散式作業系統）
    特性 提供跨網路系統間的功能；通訊機制讓不同電腦上的 process 交換訊息 提供自主性較低（less autonomous） 的環境
    使用者感受 知道有多台電腦 各電腦溝通緊密到產生「只有單一 OS 控制整個網路」的錯覺
    相關技術 訊息傳遞 process migration、data/file migration（行程／資料／檔案遷移）

    1.9 核心資料結構 (Kernel Data Structures)

    OS 實作的核心，是 OS 中使用的基本資料結構。

    串列類

    結構 中文 說明
    Array 陣列 每個元素可直接存取
    Singly linked list 單向鏈結串列 每個節點指向下一個
    Doubly linked list 雙向鏈結串列 每個節點指向前一個與下一個
    Circular linked list 環狀鏈結串列 最後一個節點指回第一個

    Stack 與 Queue

    Stack（堆疊） Queue（佇列）
    原則 LIFO（Last In, First Out，後進先出） FIFO（First In, First Out，先進先出）
    操作 push（放入）／pop（取出） 從尾端加入、從前端移除
    補充例子 疊盤子；函式呼叫時 OS 用 stack 存放參數、區域變數、返回位址 排隊結帳；印表機的列印工作、等待 CPU 的 process

    Tree（樹）

    • 用來階層式表示資料的結構。
    • Binary search tree（二元搜尋樹）：left_child ≤ right_child。
      • 搜尋的 worst case 為 O(n)（樹退化成一條鏈時）。
    • Balanced binary search tree（平衡二元搜尋樹）：
      • n 個項目最多 lg n 層。
      • worst case 為 O(lg n)。
      • 投影片例子：Linux 在 CPU 排程中使用 red-black tree（紅黑樹）。

    Hash Function 與 Hash Map（雜湊函式與雜湊表）

    • Hash function 把資料當輸入，計算後回傳一個數值，用它當索引直接找到資料。
    • 用途之一是實作 hash map（key → value 的對應）。OS 中廣泛使用。
    • 搜尋效能可達 O(1)。
    • Hash collision（雜湊碰撞）：不同的輸入算出相同的輸出。

    投影片例子：H(X) = X % 8

    • X = 6 → H(6) = 6 % 8 = 6
    • X = 14 → H(14) = 14 % 8 = 6
    • 兩個不同的 X 得到同一個位置 → hash collision。常見解法是在該位置掛一條 linked list。

    留意 補充：投影片寫「Search worst-case performance is O(1)」。依課本的說法，hash 的優勢是查找可以快到 O(1)；但若碰撞嚴重（全部擠在同一格），最差情況會退化到 O(n)。考試時建議以老師上課的說法為準，並可向老師確認。

    Bitmap（位元圖）

    • 用 n 個二進位數字表示 n 個項目的狀態。
    • 優點：非常省空間。

    投影片例子 1：001011101，以 0 表示可用、1 表示不可用

    位置 0 1 2 3 4 5 6 7 8
    bit 0 0 1 0 1 1 1 0 1

    → 資源 0、1、3、7 可用（available）；2、4、5、6、8 不可用。

    投影片例子 2：磁碟區塊的 bitmap（n 個 disk block）

    • bit[i] = 0 → block[i] free（空閒）
    • bit[i] = 1 → block[i] occupied（已佔用）

    這就是 1.5.4 提到的 free-space management 中的 bit-mapping。

    1.10 運算環境 (Computing Environments)

    1.10.1 Traditional Computing（傳統運算）

    • Stand-alone（獨立運作） 的通用機器。
    • 但界線已 blurred（模糊），因為大多數系統都與其他系統互連（Internet）。
    • Portal（入口網站）：提供以 web 存取內部系統。
    • Network computer／thin client（精簡型用戶端）：像 web 終端機。
    • 行動電腦透過無線網路互連。
    • 網路變得 ubiquitous（無所不在）——連家用系統都用 firewall（防火牆） 防禦網路攻擊。

    1.10.2 Mobile Computing（行動運算）

    • 指在手持智慧型手機、平板等裝置上的運算。
    • 與傳統筆電的功能差異：多了額外的硬體功能，如 GPS、gyroscope（陀螺儀）。
    • 因此有新型態的 App，如 augmented reality（AR，擴增實境）。
    • 連線方式：IEEE 802.11 無線網路（Wi-Fi） 或 cellular data network（行動數據網路）。
    • 主流：Apple iOS、Google Android。

    1.10.3 Client-Server Computing（主從式運算）

    Server（伺服器） 回應 client（用戶端） 產生的請求。

    類型 中文 說明 補充例子
    Compute-server system 運算伺服器系統 提供介面讓 client 請求服務（如資料庫） 網站後端的資料庫伺服器
    File-server system 檔案伺服器系統 提供檔案系統介面讓 client 存取檔案 學校的網路硬碟、NAS

    1.10.4 Peer-to-Peer Computing（P2P，對等式運算）

    • 分散式系統的另一種結構，不區分 client 與 server。
    • 所有節點都是 peer（對等節點），可以當 client、server，或兩者皆是。
    • 節點必須先加入 P2P 網路，兩種找服務的方式：
      1. 向網路上的集中式查詢服務（centralized lookup service） 註冊自己的服務
      2. 廣播（broadcast） 服務請求，並透過 discovery protocol（探索協定） 回應他人的請求
    • 投影片例子：Napster（集中式查詢）、Gnutella（廣播）、VoIP（Voice over IP） 如 Skype。

    1.10.5 Cloud Computing（雲端運算）

    雲端運算是一種基於網際網路的運算方式，使用者透過網際網路隨選租用遠端廠商所提供的資源、平台與應用系統。

    • 透過網路把運算、儲存，甚至應用程式當成服務提供。
    • 是 virtualization 的邏輯延伸（以虛擬化為基礎）。
    • 投影片例子：Amazon EC2 有數千台伺服器、數百萬個 VM、PB 等級的儲存，使用者依用量付費。

    依部署方式分類：

    類型 中文 說明
    Public cloud 公有雲 透過 Internet 提供給任何願意付費的人
    Private cloud 私有雲 公司自己營運、給公司自己用
    Hybrid cloud 混合雲 同時包含公有與私有雲的元件

    依服務模式分類重點：

    類型 全名 中文 說明 投影片例子 補充例子
    SaaS Software as a Service 軟體即服務 透過 Internet 提供一或多個應用程式 文書處理、試算表 Google Docs、Gmail
    PaaS Platform as a Service 平台即服務 透過 Internet 提供現成可用的軟體堆疊 資料庫伺服器 Heroku、Google App Engine
    IaaS Infrastructure as a Service 基礎設施即服務 透過 Internet 提供伺服器或儲存 備份用的儲存空間 Amazon EC2、S3

    補充例子（吃披薩比喻）：IaaS 是租一間有烤箱的廚房，食材和做法自己來；PaaS 是連麵團醬料都備好，你只管放料；SaaS 是直接外送到家，打開就吃。

    雲端環境的組成：傳統 OS ＋ VMM ＋ 雲端管理工具（投影片 例：VMware vCloud Director）。

    • 連上 Internet 需要 firewall 等安全措施。
    • Load balancer（負載平衡器） 把流量分散到多個應用程式。

    1.10.6 Real-Time Embedded Systems（即時嵌入式系統）

    Embedded system（嵌入式系統）：電腦硬體與軟體的組合（可能再加上機械或其他零件），設計來執行特定工作。

    • 差異很大（vary considerably）：
      • 有些有 OS（通用電腦跑標準 OS ＋ 特殊用途應用程式，功能有限）
      • 有些沒有 OS 也能執行工作
    • 嵌入式系統幾乎都跑 embedded real-time OS（嵌入式即時作業系統）。

    投影片例子（嵌入式系統清單節錄）：防鎖死煞車（ABS）、自動對焦相機、ATM、自動收費系統、數位相機、指紋辨識器、家用保全、維生系統、印表機、路由器、洗衣機、遊戲主機、機器人、自動駕駛腳踏車／汽車、無人機（drone）、iRobot 掃地機器人。

    Real-time system（即時系統）：

    • 當處理器的運作或資料流有嚴格的時間要求（rigid time requirements） 時使用。
    • 常作為專用應用中的控制裝置。
    • 有明確、固定的時間限制（well-defined, fixed time constraints）。
    • 處理必須在限制時間內完成，否則系統就算失敗。
    • 只有在時間限制內回傳正確結果，才算運作正確。

    投影片例子：科學實驗控制、醫學影像系統、工業控制系統、汽車引擎、家電控制器、武器系統。 補充例子：汽車安全氣囊必須在撞擊後幾十毫秒內彈出。晚 1 秒才算出「應該彈出」，就算答案正確也沒有意義。

    1.11 自由與開放原始碼作業系統

    Open-source vs. Closed-source

    • Open-source OS（開放原始碼作業系統）：以原始碼形式提供。
    • Closed-source（封閉原始碼）：只提供編譯後的二進位檔（binary）。

    三個容易混淆的名詞重點

    名詞 中文 重點
    Freeware 免費軟體 不用付錢就能取得，但通常有其他限制；使用者沒有使用、複製、研究、修改、散佈的自由；原始碼不一定公開
    Free Software 自由軟體 重點是自由（freedom） 而不是免費；使用者擁有四種自由
    Open Source 開放原始碼 原始碼可取得

    補充：Free 在這裡是「自由」的意思，不是「免費」。常見的說法是 free as in free speech, not free beer。

    Richard Stallman 與 FSF

    • Richard Stallman：1953 年生於美國，1971 年受聘於 MIT 人工智慧實驗室（AI Laboratory）。
    • 1984 年發起 GNU 計劃：創造一套完全自由、相容於 Unix 的作業系統 GNU（GNU's Not Unix!）。
    • 1985 年成立 FSF（Free Software Foundation，自由軟體基金會），鼓勵自由交換軟體原始碼與自由使用軟體。
    • GNU 的成果：bash、ispell、gcc、grep 等。

    自由軟體的四種自由

    自由 內容
    自由之零 不論目的為何，有使用該軟體的自由
    自由之一 有研究該軟體如何運作的自由，並可修改以符合自身需求（前提：取得原始碼）
    自由之二 有重新散佈該軟體的自由
    自由之三 有改善並再利用該軟體的自由，並可發表修訂版本讓整個社群受惠（前提：取得原始碼）

    使用者具有以上四種權利，該軟體才能稱為「自由軟體」。

    GPL（GNU General Public License，GNU 通用公共授權）

    • 自由軟體常用的授權條款。
    • 規定：原始碼必須隨二進位檔一起散佈；對原始碼做的任何修改，也必須以同樣的 GPL 釋出。
    • 精神：自由、分享、互惠——你免費取得原始碼，修改後基於公平互惠也必須公開成果。
    • 投影片例子：GNU/Linux、BSD UNIX（包含 Mac OS X 的核心）等。

    重點整理：OS 什麼時候會執行？

    這是投影片貫穿全章的主線，共四個時機（加上 timer）：

    # 時機 觸發來源 流程 例子
    (1) System booting（系統開機） 電源開啟 ROM 的 bootstrap → 載入 kernel 到 RAM → 啟動 GUI / Shell 按電源鍵
    (2) Interrupt occurs（發生中斷） 硬體裝置 interrupt vector → ISR → device driver 鍵盤輸入、磁碟讀取完成
    (3) Exception occurs（發生例外） 程式錯誤 interrupt vector → exception handler a = 5/0、存取非法記憶體
    (4) System call occurs（發生系統呼叫） 程式主動請求 trap → system call handler → service routine fork()、讀寫檔案
    (+) Timer interrupt（計時器中斷） 計時器到時 interrupt vector → timer handler → 切換 process 時間片用完、無窮迴圈

    共同點：每一次都會從 user mode 切到 kernel mode，由 OS 接手，處理完再切回 user mode。

    容易混淆的觀念對照

    比較 A B
    Interrupt vs. Trap Interrupt：通常由硬體產生，與目前執行的指令無關（非同步） Trap / Exception：由軟體產生，因錯誤或 system call 而起
    Program vs. Process 被動，磁碟上的檔案 主動，執行中的程式
    Multiprogramming vs. Multitasking 等待時才切換，目標是 CPU 使用率 時間片到就切換，目標是回應時間
    Multiprocessor vs. Clustered 多個 CPU 在同一台機器內，共享 bus／memory 多台獨立機器（node）透過網路連結，共享儲存
    SMP vs. Asymmetric MP 每個 CPU 對等，做所有工作 boss 分派工作給 worker
    UMA vs. NUMA 存取任何記憶體時間相同 存取本地記憶體較快
    Interrupt-driven I/O vs. DMA CPU 親自搬資料，每 byte 一次中斷 控制器直接搬到記憶體，每 block 一次中斷
    Protection vs. Security 控制內部資源存取的機制 防禦內外部攻擊
    Virtualization vs. Emulation 同類型 CPU，較快 不同類型 CPU，用軟體模擬，最慢
    Type 1 vs. Type 2 hypervisor 直接跑在硬體上（ESX、XenServer） 跑在 host OS 上（VirtualBox、VMware Workstation）
    Client-Server vs. P2P 角色固定：server 提供、client 請求 每個節點既是 client 也是 server
    Network OS vs. Distributed OS 使用者知道有多台電腦 讓使用者以為只有單一 OS
    Freeware vs. Free Software 免費，但無修改散佈自由 有四種自由，重點不在價格
    Buffering vs. Caching vs. Spooling 傳輸時暫存 為了效能放到較快的儲存

    (1) Built-in（內建） (2) 透過 system program

    使用者 — UNIX 採用

    2.3 系統呼叫 (System Calls)

    基本概念

    • System call（系統呼叫）：讓使用者程式請求 OS 服務的方法。
    • 是 OS 所提供服務的程式介面（programming interface）。
    • 通常以 C / C++ 寫成的 routine 提供。
    • 程式大多透過高階的 API（Application Program Interface，應用程式介面） 來使用，而不是直接呼叫 system call。

    回顧 Ch1：發生 system call 時，CPU 從 user mode 切到 kernel mode，經 interrupt vector → system call handler → system call service routine，完成後返回。

    System call 使用範例（Fig. 2.5）：複製檔案

    投影片例子：UNIX 的 cp in.txt out.txt，背後的 system call 順序：

    步驟 動作 涉及的 I/O
    1 取得輸入檔名 在螢幕顯示提示、接收輸入
    2 取得輸出檔名 在螢幕顯示提示、接收輸入
    3 開啟輸入檔 檔案不存在 → abort（中止）
    4 建立輸出檔 檔案已存在 → abort
    5 迴圈：從輸入檔讀、寫到輸出檔 直到讀取失敗（讀到檔尾）
    6 關閉輸出檔
    7 在螢幕顯示完成訊息
    8 正常結束

    一個看似簡單的複製動作，就用到一大串 system call。

    API（應用程式介面）

    三種最常見的 API：

    API 適用系統
    Win32 API Windows
    POSIX API POSIX 系統（幾乎所有版本的 UNIX、Linux、Mac OS X）
    Java API Java 虛擬機器（JVM）
    • POSIX（Portable Operating System Interface，可攜式作業系統介面）：IEEE Computer Society 制定的一系列標準，用來維持作業系統之間的相容性。

    為什麼用 API 而不直接用 system call？

    1. Program portability（程式可攜性）：同一份程式可在支援相同 API 的系統上編譯執行。
    2. 實際的 system call 通常更瑣碎、更難用。

    投影片例子：標準 API read()（在命令列用 man read 查詢）

    #include <unistd.h>

    部分 說明
    ssize_t return value（回傳值）：成功時回傳讀到的 byte 數；0 表示檔尾；錯誤回傳 -1
    read function name（函式名稱）
    int fd 要讀取的 file descriptor（檔案描述子）
    void *buf 資料要讀進去的 buffer
    size_t count 最多讀進 buffer 的 byte 數

    RTE 與 System-call Interface

    • RTE（Run-Time Environment，執行時期環境）：執行某種程式語言寫的應用程式所需的整套軟體，包含 compiler 或 interpreter，以及 library、loader 等。
    • RTE 提供 system-call interface（系統呼叫介面），作為連結 OS 所提供 system call 的橋樑。
    • System-call interface 會攔截（intercept） API 中的函式呼叫，再去呼叫 OS 內必要的 system call。

    API – System Call – OS 的關係（Fig. 2.6）

    • 每個 system call 通常對應一個編號（number）。
    • System-call interface 維護一張依編號索引的表（system call table）。
    • 它呼叫 kernel 中對應的 system call，並回傳狀態與回傳值。
    • 呼叫者不需要知道 system call 如何實作，只要遵守 API、了解 OS 會回傳什麼即可。

    投影片例子：Standard C Library C 程式呼叫 printf("Greetings") → C 函式庫攔截 → 呼叫 write() system call → kernel 執行 → 結果一路回傳給程式。 printf() 是 library call（函式庫呼叫），write() 才是 system call。

    Linux/x86 的 System Call 實作

    • 使用者 process 請求 kernel 提供的服務（例如開檔）時，就發生 system call。
    • 在 x86 CPU 上，使用者 process 用 software interrupt（軟體中斷） 通知 kernel。
    • 使用的中斷編號是 0x80（位於 IDT，Interrupt Descriptor Table，中斷描述表；32 位元 CPU）。
    • 流程：標準 C 函式庫把要傳遞的參數載入 CPU registers，然後觸發 int 0x80。
    • 因此 system_call 函式其實是一個 interrupt handler（中斷處理常式）。

    參數傳遞（Parameter Passing）重點

    Process 與 OS 之間傳遞 parameter（參數） 的三種方法：

    方法 說明 特點
    1. Registers（暫存器） 直接把參數放在暫存器 最簡單，但參數的數量或長度受限
    2. Block / Table（區塊／表格） 把參數存在記憶體中的一塊區域，再把該區塊的位址放在暫存器傳過去 Linux 與 Solaris 採用
    3. Stack（堆疊） 程式把參數 push 到 stack，OS 再 pop 出來 不限制參數的數量或長度

    投影片例子（Fig. 2.7）：user program 把參數放在記憶體的表格 X，把 X 的位址載入 register，然後發出 system call 13；OS 執行 13 號 system call 的程式碼時，依 register 中的位址到表格 X 取出參數。

    補充例子：方法 1 像直接把三樣東西拿在手上遞過去（手只有兩隻，東西多了拿不了）；方法 2 像把東西放進置物櫃，只把櫃子號碼告訴對方。

    Communication Models（通訊模型）重點

    IPC（Interprocess Communication，行程間通訊） 有兩種常見模型：

    Message-Passing Model（訊息傳遞模型）

    • 透過 OS 提供的 IPC 設施交換資訊；訊息經由 kernel 轉送（kernel 內有 message queue）。
    • 訊息可以在 process 間直接交換，或透過共用的 mailbox（信箱） 間接交換。
    • 通訊的 process 可以在同一台或不同機器上。
    • 必須先開啟連線（connection）。
    • Naming（命名）：要知道對方是誰
      • Host name：get_hostid()
      • Process name：get_processid()
    • 相關 system call：open connection、accept connection、wait for connection、read / write messages、close connection。
    • Daemon（常駐程式）：專門等待連線的系統程式。接收連線的是 server，發起的是 client。

    Shared-Memory Model（共享記憶體模型）

    • 用 shared_memory_create() 與 shared_memory_attach() 建立並取得其他 process 擁有的記憶體區域的存取權。
    • 一般情況 OS 會阻止 process 存取別人的記憶體，所以需要兩個以上的 process 同意移除這項保護限制。
    • 之後就能在共享區域讀寫資料來交換資訊。
    • 資料的格式與位置由這些 process 自己決定，不受 OS 控制。
    • Process 要自己負責不同時寫入同一位置——需要 protection 與 synchronization（同步）。

    兩種模型比較

    Message Passing Shared Memory
    資料路徑 經過 kernel 直接讀寫共享區域，不經 kernel
    適合 交換少量資料 大量資料、需要高速
    優點 不需要避免衝突；跨電腦通訊較容易實作 速度最快、最方便（在同一台電腦內以記憶體傳輸速度進行）
    缺點 較慢（每次都要 system call） 需要自行處理 protection 與 synchronization

    補充例子：

    • Message passing 像寄信：信交給郵差（kernel）轉送，安全但慢；可以寄到別的城市（別台電腦）。
    • Shared memory 像辦公室的共用白板：兩人直接在上面寫和看，很快；但兩人同時寫同一格就會亂掉，要先約好規則。

    從原始碼到在記憶體中執行的過程：

      │  compiler        gcc -c main.c
      ▼
object file             main.o         ← relocatable object file
      │  linker          gcc -o main main.o -lm
      │  ◄── other object files / libraries
      ▼
executable file         main
      │  loader          ./main
      │  ◄── dynamically linked libraries
      ▼

    元件 中文 工作
    Compiler 編譯器 把原始碼編譯成 object file（目的檔）
    Relocatable object file 可重定位目的檔 設計成可以載入到任何實體記憶體位置的目的檔
    Linker 連結器 把多個目的檔合併成單一的 binary executable file（二進位可執行檔）；也會把 library 帶進來
    Loader 載入器 程式平時以二進位可執行檔存在輔助儲存；要執行時由 loader 載入記憶體
    Relocation 重定位 為程式各部分指定最終位址，並調整程式中的程式碼與資料以符合這些位址

    Dynamic linking（動態連結）：

    • 現代通用系統不會把 library 連結進可執行檔。
    • 而是使用 DLL（Dynamically Linked Library，動態連結函式庫），在需要時才載入。
    • 使用同一版本 library 的所有程式共享同一份（只載入一次）。

    標準格式：目的檔與可執行檔有標準格式，OS 才知道如何載入並啟動（Linux 用 ELF，Executable and Linking Format）。

    投影片例子：gcc -c main.c 產生 main.o；gcc -o main main.o -lm 連結數學函式庫（-lm）產生 main；./main 時由 loader 載入執行。 補充例子：Windows 上程式啟動時跳出「找不到 xxx.dll」，就是 loader 在執行時找不到要動態連結的函式庫。

    2.6 為什麼應用程式綁定特定 OS

    • 在某個系統上編譯的 App，通常無法在其他 OS 上執行。
    • 原因：每個 OS 提供自己獨特的 system call，還有自己的檔案格式等等。

    讓 App 能跨多個 OS 執行的三種方法：

    方法 說明 例子
    1. 直譯式語言 用 interpreted language 寫，只要各 OS 上有該語言的 interpreter Python、Ruby
    2. 虛擬機器 語言本身包含一個 VM，App 在 VM 裡執行 Java
    3. 標準語言＋各自編譯 用標準語言寫，在每個 OS 上分別編譯 C

    補充例子：Windows 的 .exe 拿到 macOS 上不能直接執行；但同一份 hello.py 在 Windows、macOS、Linux 只要裝了 Python 就能跑。

    2.7 作業系統的設計與實作

    OS 的設計與實作沒有完整的解答，但有些方法已被證明成功。

    2.7.1 Design Goals（設計目標）

    • 先定義目標與規格，會受到硬體選擇與系統類型影響（傳統桌機／筆電、行動、分散式、即時）。
    User goals（使用者目標） System goals（系統目標）
    觀點 使用系統的人 設計、建造、維護系統的人
    要求 convenient to use（方便使用）、easy to learn（容易學）、reliable（可靠）、safe（安全）、fast（快速） easy to design, implement, maintain（容易設計、實作、維護）；flexible（有彈性）、reliable、error-free（無錯誤）、efficient（有效率）

    2.7.2 Mechanisms and Policies（機制與策略）重點

    把 policy 與 mechanism 分開是設計 OS 非常重要的原則。

    Mechanism（機制） Policy（策略）
    決定 How to do something（如何做） What will be done（要做什麼）
    • 好處：日後策略要改變時，有最大的彈性——只改 policy，不用動 mechanism。

    投影片例子：timer 是確保 CPU 保護的 mechanism；而「某個使用者的 timer 要設多久」是 policy 的決定。 補充例子：紅綠燈的燈號切換裝置是 mechanism；「這個路口紅燈要 60 秒還是 90 秒」是 policy。交通局想調整秒數，不需要換一組紅綠燈。

    2.7.3 Implementation（實作）

    • 早期 OS 用 assembly language（組合語言） 寫，現在大多用 C 或 C++ 等高階語言。
    • 實際上通常混用多種語言：
      • 最底層：assembly
      • 主體：C
      • 系統程式：C、C++、腳本語言（PERL、Python、shell script）

    用高階語言寫的優缺點：

    優點 缺點
    寫得更快 速度降低
    程式碼更精簡（compact） 儲存空間需求增加
    更容易理解與除錯
    可使用更好的資料結構與演算法
    容易 port（移植） 到其他硬體

    2.8 作業系統結構 (Operating-System Structure)

    • OS 既大又複雜，modularity（模組化） 很重要。
    • 常見做法：把 OS 切成小的元件或 module（模組），而不是一整塊。
    • 每個模組都應該是系統中定義明確的部分，有仔細定義的輸入、輸出與功能。

    系統元件互相連結並融合（meld） 成 kernel 的方式有五種：

    2.8.1 Monolithic Structure（單體式結構）

    Monolithic ＝ 獨塊巨石的、整體的、龐大的。

    • 最簡單的組織方式就是完全沒有結構。
    • 把 kernel 的所有功能放進單一、靜態的二進位檔，在單一 address space（位址空間） 中執行。
    • 一開始是小而簡單、功能有限的系統，後來成長超出原本的範圍。
    • OS 被寫成一堆 procedure 的集合，任何一個都可以在需要時呼叫其他任何一個。

    投影片例子：原始 UNIX 受限於當時的硬體功能，結構有限，由兩個可分離的部分組成：

    1. Systems programs
    2. Kernel：system-call interface 之下、實體硬體之上的所有東西；提供檔案系統、CPU 排程、記憶體管理等功能——大量功能被合併在同一層。

    傳統 UNIX 結構（比 simple 複雜但未完全分層）：

                     (the users)
  shells and commands / compilers and interpreters / system libraries
  ════════ system-call interface to the kernel ════════
  signals, terminal handling │ file system        │ CPU scheduling
  character I/O system       │ swapping, block I/O│ page replacement
  terminal drivers           │ disk & tape drivers│ demand paging, virtual memory
  ════════ kernel interface to the hardware ════════
  terminal controllers │ device controllers │ memory controllers

    投影片例子：Linux 是 monolithic plus modular design——applications / glibc → system-call interface → (file systems、CPU scheduler、networks (TCP/IP)、memory manager、block devices、character devices) → device drivers → hardware。

    優點 缺點
    效能優勢明顯：system-call interface 的 overhead 很小，kernel 內部通訊很快 難以實作與擴充
    所有功能擠在一層，一個地方出錯可能拖垮整個系統

    儘管有這些缺點，monolithic kernel 的速度與效率說明了為什麼 UNIX、Linux、Windows 至今仍看得到這種結構。

    投影片例子：修改 Linux 核心後重新編譯（make all、make modules_install、make install、reboot），若設定有誤可能出現 Booting has failed 或 Kernel Panic，要重開機並在核心選單改選原本的核心。

    2.8.2 Layered Approach（分層式）

    • OS 被切成許多 layer（層），每一層建立在較低層之上。
    • 最底層（layer 0）是硬體；最高層（layer N）是使用者介面。
    • 每一層只能使用較低層的函式與服務。
      layer N   user interface
     ⋮
  layer 1
  layer 0   hardware

    投影片例子：Application Programs → (user / kernel mode 分界) → System Services → File System → Memory and I/O Device Management → Processor Scheduling → Hardware。

    優點 缺點
    建構與除錯簡單 需要仔細規劃：必須適當定義每一層的功能，因為一層只能用它下面的層
    簡化除錯與系統驗證（從最底層逐層往上測，出錯一定在當前這層） 效率較差：層越多、overhead 越大、越慢。每一層都替 system call 增加負擔
    簡化系統的設計與實作
    • 很少 OS 採用純粹的分層式。
    • 現在的趨勢：設計較少的層、每層較多功能，保有模組化程式碼的大部分優點，同時避免層的定義與互動問題。

    補充例子：像公司公文一層一層往上簽。責任清楚、容易找出哪一關出問題；但每多一層就多一道手續，速度變慢。

    2.8.3 Microkernels（微核心）

    • 1980 年代中期，CMU（卡內基美隆大學） 開發了 Mach，用 microkernel 方法把 kernel 模組化。
    • 做法：把所有非必要的元件從 kernel 移除，改以使用者層級程式（user-level program） 實作，各自在獨立的位址空間。
    • Microkernel 通常只提供：
      • 最基本的 process management
      • 最基本的 memory management
      • communication facility（通訊設施）
    • 主要功能：在 client 程式與各種同樣在 user space 執行的服務之間提供通訊。
    • 通訊透過 message passing。
      ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
  │ Application │   │ File System │   │Device Driver│   user mode
  └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
         └──── messages ───┴─── messages ────┘
  ┌─────────────────────────────────────────────────┐
  │ IPC │ memory management │ CPU scheduling        │   kernel mode
  │                  microkernel                    │
  └─────────────────────────────────────────────────┘
                       hardware
    優點 缺點
    容易擴充（新服務加在 user space，不必改 kernel） 效能下降：系統功能的 overhead 增加
    容易把 OS 移植到新架構 user space 與 kernel space 之間通訊的負擔（訊息要複製、要切換 process）
    更安全、可靠（大部分服務以 user process 執行；某個服務掛掉不會拖垮整個 OS）

    投影片例子：

    • Darwin（macOS 與 iOS 的 kernel 元件）部分以 Mach kernel 為基礎。
    • QNX Neutrino microkernel。
    • Windows 的演變：Windows NT（分層式 microkernel 組織）→ Windows NT 4.0（把一些層從 user space 搬到 kernel space 並更緊密整合）→ Windows XP（比較像 monolithic 而不是 microkernel）。原因就是效能。

    2.8.4 Modules（模組）

    • 目前 OS 設計可能最好的方法是使用 LKM（Loadable Kernel Module，可載入核心模組）。
    • Kernel 有一組核心元件，可以在開機時或執行期間透過模組連結額外的服務。
    • 現代 UNIX 實作（Linux、macOS、Solaris）以及 Windows 都很常見。
    • Kernel 提供核心服務，其他服務在 kernel 執行時動態實作。

    投影片例子：Solaris loadable modules——core Solaris kernel 周圍掛著：scheduling classes、file systems、loadable system calls、executable formats、STREAMS modules、miscellaneous modules、device and bus drivers。

    與其他結構的比較：

    比較對象 相似處 模組方式更好的地方
    Layered 每個 kernel 區段都有定義明確、受保護的介面 更有彈性：任何模組都可以呼叫其他任何模組
    Microkernel 主模組只有核心功能，以及如何載入其他模組、與之通訊的知識 更有效率：模組之間通訊不需要 message passing

    Linux 的 LKM

    • Linux 使用 LKM，主要用來支援 device driver 與 file system。
    • LKM 可以在執行期間插入（insert） 或移除（remove）。
    • 讓 kernel 具有動態與模組化的特性，同時保有 monolithic 系統的效能優勢。

    擴充 Linux kernel 的兩種方式重點：

    (1) 直接修改 kernel 原始碼 (2) 使用 LKM
    做法 加入程式碼 → 編譯連結安裝（make all、make modules_install、make install）→ 重開機 把模組在執行期間直接載入 kernel
    kernel 大小 加入的程式碼永久增加 kernel 大小 可隨時卸載，不會永久影響 kernel 大小
    編譯 整個 kernel 都要重新編譯 模組可以單獨編譯
    重開機 需要 不需要

    Linux 模組的特性：

    • Kernel 編譯時要啟用 loadable module 支援。
    • 模組是 ELF（Executable and Linking Format）object code。
    • 執行期間插入／移除的命令：insmod、rmmod。
    • 模組是 kernel 的一部分，不是 process（位於 kernel space）。
    • 至少要有 2 個函式：init 與 exit。

    投影片例子：

    insmod hello.ko     # 裝載 module
rmmod hello.ko      # 卸載 module
cat /var/log/messages   # 查看系統資訊

    在 /var/log/messages 中可看到 kernel: Hello, world 與 kernel: Goodbye, module world，表示成功裝載與卸載。

    補充例子：對應上面輸出的最小模組大致長這樣（示意用，我沒有在這裡實際編譯測試；實作時以老師給的範例與你的 kernel 版本為準）：

    #include <linux/init.h>
#include <linux/module.h>
#include <linux/kernel.h>

MODULE_LICENSE("GPL");

static int __init hello_init(void)      /* insmod 時執行 */
{
    printk(KERN_INFO "Hello, world\n");
    return 0;
}

static void __exit hello_exit(void)     /* rmmod 時執行 */
{
    printk(KERN_INFO "Goodbye, module world\n");
}

module_init(hello_init);
module_exit(hello_exit);

    模組在 kernel space 執行，所以用 printk() 而不是 printf()，輸出會進系統 log 而不是螢幕。較新的 Ubuntu 通常用 dmesg 或 journalctl -k 查看，而不是 /var/log/messages。

    2.8.5 Hybrid Systems（混合式系統）

    • 很少 OS 採用單一、嚴格定義的結構。
    • 大多數 OS 結合不同結構，成為 hybrid system，以兼顧 performance（效能）、security（安全）、usability（易用性）。
    OS 結構特性
    Linux Monolithic：整個 OS 在單一 kernel 位址空間，效能非常好。
    同時 modular：新功能可動態加入 kernel
    Windows 大體上 monolithic（效能考量）。
    保留一些 microkernel 的行為：支援以 user-mode process 執行的獨立 subsystem（稱為 personalities）。
    也支援動態 loadable kernel module

    macOS 與 iOS

    架構（由上到下）：

    層 中文 說明
    applications 應用程式
    user experience 使用者體驗層 macOS 用 Aqua；iOS 用 Springboard
    application frameworks 應用程式框架 Cocoa（macOS）／Cocoa Touch（iOS），提供 Objective-C API
    core frameworks 核心框架 圖形、多媒體等
    kernel environment (Darwin) 核心環境

    iOS：

    • Apple 給 iPhone、iPad 的行動 OS。
    • 以 Mac OS X 為基礎，加上行動裝置的功能。
    • 不能直接執行 Mac OS X 應用程式；CPU 架構也不同（ARM vs. Intel）。
    • 各層：Cocoa Touch（開發 App 的 Objective-C API）→ Media services（圖形、音訊、視訊）→ Core services（雲端運算、資料庫）→ Core OS（以 Mac OS X kernel 為基礎）。

    Darwin 的結構（hybrid）：

              applications
        library interface
   Mach traps │ BSD (POSIX) system calls
   ─────────────────────────────────────
   scheduling │ IPC │ memory management
   iokit                Mach kernel
   kexts
    • 是一個分層系統，主要由 Mach microkernel 與 BSD UNIX kernel 組成。
    • 提供兩套 system-call 介面：Mach traps 與 BSD (POSIX) system calls。
    • Kernel 環境提供 I/O Kit 開發 device driver，以及動態可載入模組，稱為 kernel extension（kext，核心擴充）。
    • Darwin 把 Mach、BSD、I/O Kit 與所有 kext 合併在單一位址空間。
    • 所以這裡的 Mach 不是純粹的 microkernel。
    • Mach 內部仍有 message passing，但不需要複製資料，因為各服務存取的是同一個位址空間——這樣解決了 microkernel 的效能問題。

    Android

    • 由 Open Handset Alliance（開放手機聯盟）（主要由 Google 主導）設計，為 Android 智慧型手機與平板開發。Open source。
    • 與 iOS 類似：是一個分層的軟體堆疊（layered stack of software），提供豐富的框架來開發行動應用。
    • 以 ART（Android RunTime）虛擬機器為基礎：
      • App 用 Java ＋ Android API 開發。
      • Java class 檔 → 編譯成 Java bytecode → 轉譯成可在 ART 上執行的檔案。
    • Libraries 包含：web browser 框架（webkit）、資料庫（SQLite）、網路支援如 SSL（secure sockets）。

    架構（由上到下）：

    層 說明
    applications 應用程式
    ART VM / Android frameworks / JNI 執行環境、框架、Java Native Interface（讓 Java 呼叫原生程式碼）
    native libraries SQLite、openGL、webkit、surface manager、SSL、media framework
    HAL（Hardware Abstraction Layer） 硬體抽象層：把實體硬體抽象化，讓 App 開發者不必管不同硬體的差異
    Bionic Google 為 Android 開發的標準 C 函式庫
    Linux kernel

    2.9 建置與啟動作業系統 (Building & Booting an OS)

    2.9.1 Operating-System Generation（作業系統生成）

    • OS 通常設計成能在一整類機器上執行，所以必須針對每個特定的電腦環境做設定或生成。這個過程稱為 SYSGEN（System Generation，系統生成）。

    SYSGEN 程式取得硬體組態資訊的方式：

    • 讀取指定的檔案
    • 詢問系統操作員
    • 直接探測（probe） 硬體

    需要決定的事項：

    • 使用什麼 CPU？
    • 開機磁碟如何格式化？
    • 有多少記憶體可用？
    • 有哪些裝置可用？
    • 需要哪些 OS 選項、使用什麼參數值？

    建立系統的三種方式：

    方式 做法 特性
    (a) Recompile 修改原始碼後完全重新編譯 最貼合硬體、系統最小；但修改最麻煩
    (b) 選擇預先編譯的模組 從 precompiled library 選出需要的模組並連結成 OS 不必重編，生成較快；系統可能較大而通用
    (c) 完全模組化 建構完全模組化的系統，在執行期選擇模組 最有彈性；硬體變更時最容易調整

    主要差異在於：生成系統的大小與通用性（generality），以及硬體組態變更時修改的難易度。

    一般情況：買來的電腦通常已經裝好 OS，但也可以自己建置並安裝其他 OS。

    從零開始生成 OS 的步驟：

    1. 撰寫 OS 原始碼
    2. 針對要執行的系統設定（configure） OS
    3. 編譯（compile） OS
    4. 安裝（install） OS
    5. 啟動（boot） 電腦及新的 OS

    投影片例子：Building and Booting Linux

    步驟 命令 產生
    1. 下載原始碼 從 http://www.kernel.org
    2. 設定 kernel make menuconfig .config 設定檔
    3. 編譯 kernel make vmlinuz（kernel image）
    4. 編譯 kernel modules make modules 依 .config 的參數編譯
    5. 安裝 kernel modules make modules_install
    6. 安裝新 kernel make install

    2.9.2 System Boot（系統開機）

    問題：硬體怎麼知道 kernel 在哪裡、怎麼載入？

    • Booting（開機）：藉由載入 kernel 來啟動電腦的程序。
    • Bootstrap program／boot loader（啟動程式／開機載入器）：
      • 一小段程式碼，存在 ROM 或 EEPROM。
      • 找到 kernel → 載入記憶體 → 開始執行。
    • Kernel 初始化硬體後，掛載 root file system（根檔案系統）。

    單階段 vs. 多階段開機

    類型 流程
    單階段 ROM 中的 bootstrap loader 直接從磁碟載入 kernel image 到 RAM
    Multistage boot（多階段開機） ① 執行非揮發性韌體（BIOS）中的小型初始 boot loader
    ② 它從磁碟固定位置 boot block（開機區塊） 載入第二個 boot loader
    ③ boot block 中的程式可能已足夠複雜，能把整個 OS 載入記憶體並開始執行；或只是再去載入更完整的 bootstrap 程式
    ④ 最後載入 kernel image
    • PC 採用多階段：簡單的 bootstrap loader 從磁碟取出較複雜的 boot program，再由它載入 kernel。
    • GRUB（Grand Unified Bootloader）：Linux 系統上的開放原始碼 bootstrap 程式。

    投影片例子：GRUB 開機選單（Ubuntu 16.04 在 VMware 上），列出多個可選的 kernel：

    *Ubuntu, with Linux 4.4.21
 Ubuntu, with Linux 4.4.21 (upstart)
 Ubuntu, with Linux 4.4.21 (recovery mode)
 Ubuntu, with Linux 4.4.0-31-generic
 ...

    用上下鍵選擇、Enter 開機、e 編輯命令、c 進入命令列。自己編譯新 kernel 後，就是在這裡選擇要用哪一個開機；新 kernel 開不起來時，也是回到這裡選舊的。

    BIOS vs. UEFI

    BIOS UEFI（Unified Extensible Firmware Interface，統一可延伸韌體介面）
    開機過程 多階段 單一、完整的 boot manager
    速度 較慢 較快
    支援 較舊 對 64 位元系統與大容量磁碟支援較好

    現代系統以 UEFI 取代 BIOS。

    2.10 作業系統除錯 (Operating-System Debugging)

    Debugging（除錯）：找出並修正錯誤（bug）。

    錯誤資訊的來源

    名詞 中文 說明
    Log file 紀錄檔 OS 產生，包含錯誤資訊
    Core dump 核心傾印 應用程式失敗時產生，擷取該 process 的記憶體
    Crash dump 當機傾印 OS 失敗（crash）時產生，包含 kernel 記憶體

    Kernighan's Law："Debugging is twice as hard as writing the code in the first place. Therefore, if you write the code as cleverly as possible, you are, by definition, not smart enough to debug it." （除錯比寫程式難一倍。所以如果你把程式寫得盡可能巧妙，照定義來說，你就不夠聰明去替它除錯。）

    Performance Tuning（效能調校）

    • 除了當機之外，效能調校可以讓系統效能最佳化。
    • 目標：移除 bottleneck（瓶頸） 來改善效能。
    • OS 必須提供計算並顯示系統行為量測值的方法。
    • 兩種方法：
      • Trace listing（追蹤列表）：記錄活動以供分析。
      • Profiling（剖析）：週期性地取樣 instruction pointer，找出統計趨勢（看程式時間都花在哪）。

    投影片例子：UNIX 的 top 程式（顯示 load average、Tasks、CPU 使用率、Mem、Swap，以及各 process 的 PID、%CPU、%MEM）；Windows 的 Task Manager（工作管理員）。

    Tracing（追蹤）

    針對特定事件收集資料，例如一次 system call 呼叫所涉及的步驟。

    工具 用途
    strace 追蹤某個 process 所呼叫的 system call
    gdb 原始碼層級的 debugger
    perf Linux 效能工具集
    tcpdump 收集網路封包

    補充例子：strace ls 可以看到 ls 這個命令背後實際呼叫了哪些 system call（openat、read、write、close…），正好對應 2.3 節的內容。

    BCC（BPF Compiler Collection）

    • 要除錯 user-level 與 kernel 程式碼之間的互動，若沒有能同時理解兩者並能插入探測（instrument） 的工具組，幾乎不可能。
    • BCC 是為 Linux 提供追蹤功能的豐富工具組（另見原始的 DTrace）。
    • 工具涵蓋整個系統各層：Applications、System Libraries、System Call Interface、VFS、File Systems、Sockets、TCP/UDP、Scheduler、Virtual Memory、Device Drivers 等。

    3.1 行程概念 (Process Concept)

    Process：a program in execution（執行中的程式）。Process 需要資源：CPU time、memory、files、I/O devices。

    從程式到行程

     program (原始碼)  ──compile & link──►  executable image  ──load into memory──►  process
                                         (可執行映像檔)                          (在 RAM 中)

    Executable image（可執行映像檔） 的組成：

    部分 中文 內容
    Header 標頭 entry point、執行檔大小、text section 的大小與起始位址、data section 的大小與起始位址
    Text section 文字區段（程式碼區段） 指令；通常是唯讀（read-only）、可執行
    Data section 資料區段 可讀寫（read/write）
    • Entry point（進入點）：text segment 中開始執行的位址。

    投影片例子：

    #include <stdio.h>
int a = 3;          // 全域變數 → data section
void main()
{                   // main 的指令 → text section
    a = 5;
    printf("a=%d", a);
}

    Loading（載入）：用二進位檔（executable image）中的區段初始化記憶體，並額外加上：

    • Stack（堆疊）：stack frame、區域變數
    • Heap（堆積）：動態配置的資料（例如 malloc）

    所以一個 process（執行中的程式）至少有 4 個區段：text、data、stack、heap。

    3.1.1 The Process

    Process 不只是程式碼（text section），還包含：

    組成 中文 內容
    Current activity 目前的活動 program counter（程式計數器） 的值、處理器 registers（暫存器） 的內容
    Process stack 行程堆疊 暫時性資料：函式參數（parameters）、返回位址（return address）、區域變數（local variables）
    Data section 資料區段 全域變數（global variables）
    Heap 堆積 執行期間動態配置的記憶體

    Process in Memory（Fig. 3.1）重點

      max ┌──────────┐
      │  stack   │   ↓ 往低位址成長
      │    ↓     │
      │          │
      │    ↑     │
      │   heap   │   ↑ 往高位址成長
      ├──────────┤
      │   data   │
      ├──────────┤
      │   text   │
    0 └──────────┘

    投影片例子：各變數放在哪裡？

    int a = 3;                    // a：全域變數 → data
main()
{
    int ret;                  // ret：區域變數 → stack
    char *ptr;                // ptr 這個指標本身：區域變數 → stack

    ptr = malloc(1000);       // 配置的 1000 bytes → heap
    ptr[10] = 'b';
    ret = func(a, 5);         // 呼叫時在 stack 上建立新的 stack frame
    printf("%d", ret);
    return;
}

int func(int p1, int p2)      // p1, p2：參數 → stack
{
    int sum;                  // sum：區域變數 → stack
    sum = p1 + p2;
    return sum;
}

    呼叫 func(a, 5) 時，stack 上依序放入 parameters（3 和 5）、return address（回到 main 的哪一行）、local variables（sum），SP（Stack Pointer，堆疊指標） 隨之移動；函式返回時這個 frame 被移除。

    Process 是 active entity（主動實體）：有一個 program counter 指出下一道要執行的指令，以及一組相關的資源。CPU 中的 sp、pc、base、limit 等暫存器記錄目前執行中 process 的狀態。

    其他重點：

    • 程式透過 GUI 滑鼠點擊、命令列輸入名稱等方式開始執行。
    • 兩個 process 可以對應同一個程式，但被視為兩個獨立的執行序列：text section 相同，但 data、heap、stack 不同。
    • Process 執行時也可以 spawn（衍生） 出許多 process。
    • Process 本身可以是其他程式碼的執行環境。

    投影片例子：JVM（Java Virtual Machine） 以一個 process 的形式執行，負責解譯載入的 Java 程式碼並代為採取動作。例如執行編譯好的 Program.class。層次：Java Program → JVM → OS。 補充例子：同時開兩個記事本視窗，就是同一個程式 notepad.exe 的兩個 process，各自編輯不同的內容。

    3.1.2 Process State（行程狀態）重點

    Process 執行時會改變狀態：

    狀態 中文 說明
    New 新建 Process 正在被建立
    Running 執行 指令正在被執行
    Waiting 等待 等待某個事件發生（如 I/O 完成、收到 signal）
    Ready 就緒 等待被分配給處理器
    Terminated 終止 執行完畢

    狀態轉換圖（Fig. 3.2）：

       new ──admitted──►  ready  ◄──────interrupt───────  running ──exit──► terminated
                        │  ────scheduler dispatch────►   │
                        ▲                                │
         I/O or event   │                                │  I/O or event wait
          completion    └──────────  waiting  ◄──────────┘
    轉換 觸發原因
    new → ready admitted：被系統接受
    ready → running scheduler dispatch：排程器選中並分派 CPU
    running → ready interrupt：被中斷（如時間片用完）
    running → waiting I/O or event wait：要等 I/O 或事件
    waiting → ready I/O or event completion：等的事情完成了
    running → terminated exit：執行結束

    重點 注意：waiting 不會直接回到 running，一定先回 ready 再等排程。任一時刻每個 CPU core 上只有一個 process 是 running，但可以有很多個 ready 和 waiting。

    補充例子：去醫院看病——掛號（new）→ 候診區等叫號（ready）→ 進診間看診（running）→ 醫生叫你去抽血等報告（waiting）→ 報告出來後回候診區（ready）→ 再進診間（running）→ 看完離開（terminated）。

    3.1.3 Process Control Block（PCB，行程控制區塊）重點

    • OS 用一個 PCB 代表每個 process，又稱 task control block。
    • PCB 是一個資料結構，存放與特定 process 相關的資訊。
    欄位 中文 內容
    Process state 行程狀態 new、ready、running、waiting、halted…
    Program counter 程式計數器 這個 process 下一道要執行的指令位址
    CPU registers CPU 暫存器 發生中斷時必須連同 program counter 一起保存，之後才能正確繼續執行
    CPU-scheduling information CPU 排程資訊 priority（優先權）、指向排程佇列的指標、排程參數
    Memory-management information 記憶體管理資訊 base 與 limit 暫存器、page table、segment table…
    Accounting information 記帳資訊 已用時間、時間限制、帳號、process 編號…
    I/O status information I/O 狀態資訊 配置給此 process 的 I/O 裝置清單、已開啟檔案清單…

    補充例子：PCB 像醫院裡每位病人的病歷。醫生換看下一位病人前，把目前病人的狀況記在病歷上；之後再輪到他時，翻開病歷就能從上次的地方繼續。

    3.1.4 Threads（執行緒）

    • 傳統上，一個 process 是執行單一 thread of execution（執行緒） 的程式，一次只能做一件事。
    • 大多數現代 OS 擴充了 process 的概念，允許一個 process 有多個執行緒，一次能做多件事。
    • 做法：每個 process 有多個 program counter，多個位置可以同時執行。
    • 支援 thread 的系統中，PCB 會擴充以包含每個 thread 的資訊。
    • 詳見 Chapter 4。

    投影片例子：Linux 的 process 表示法——C 結構 task_struct

    pid_t pid;                    /* process identifier（行程識別碼） */
long state;                   /* state of the process（狀態） */
struct sched_entity se;       /* scheduling information（排程資訊） */
struct task_struct *parent;   /* this process's parent（父行程） */
struct list_head children;    /* this process's children（子行程串列） */
struct files_struct *files;   /* list of open files（已開啟檔案） */
struct mm_struct *mm;         /* address space of this process（位址空間） */

    這就是 Linux 中 PCB 的實作。

    3.2 行程排程 (Process Scheduling)

    目標
    Multiprogramming 隨時都有 process 在執行，最大化 CPU 使用率
    Time sharing 讓 CPU 在 process 之間頻繁切換，使用者能在程式執行時與之互動

    Process scheduler（行程排程器）：從可用的 process 中選一個，放到某個 core 上執行。

    3.2.1 Scheduling Queues（排程佇列）

    佇列 中文 說明
    Ready queue 就緒佇列 Process 進入系統後放在這裡，已就緒、等待在 CPU core 上執行
    Wait queue 等待佇列 等待某事件發生（如 I/O 完成）的 process 放在這裡

    實作（Fig. 3.4）：佇列通常用 linked list 實作。queue header 有 head 與 tail 指標，把各個 PCB 串起來。

    投影片例子：ready queue：head → PCB₇ → PCB₂；wait queue：head → PCB₃ → PCB₁₄ → PCB₆。

    Queueing diagram（佇列圖，Fig. 3.5）：

                ┌────────────────────────────────────────────────┐
            ▼                                                │
       ready queue ───dispatch──► CPU ──────────────────────►  (結束離開)
            ▲                      │
            ├── I/O ◄── I/O wait queue ◄── I/O request ──────┤
            ├───────────────────────── time slice expired ◄──┤
            ├── child terminates ◄── child termination ◄── create child process
            │                        wait queue              │
            └── interrupt occurs ◄── interrupt ◄── wait for an interrupt
                                     wait queue

    Process 被分派到 CPU 後，可能發生四件事：

    事件 結果
    發出 I/O request 進入 I/O wait queue，I/O 完成後回 ready queue
    Time slice expired（時間片用完） 直接回 ready queue
    Create child process 並等它結束 進入 child termination wait queue
    Wait for an interrupt 進入 interrupt wait queue

    3.2.2 CPU Scheduling（CPU 排程）

    • Process 在生命週期中會在各個排程佇列間遷移（migrate）。
    • CPU scheduler（CPU 排程器）：
      • 從 ready queue 選一個 process，分配 CPU core 給它。
      • 執行非常頻繁（例如至少每 100 毫秒一次），所以必須很快。

    Swapping（置換）——一種中間形式的排程：

    • 把 process 從記憶體移出（也就退出對 CPU 的競爭），藉此降低 degree of multiprogramming（多元程式度），即記憶體中 process 的數量。
    • Swap out：把 process 從記憶體移到磁碟，保存目前狀態。
    • Swap in：之後從磁碟搬回記憶體，恢復狀態。
    • 通常只在記憶體被 overcommitted（過度配置） 而必須釋放時才需要。

    投影片例子：Process A 佔用的記憶體被 swap out 到磁碟的 4–7 號區塊；Process B 從磁碟的 17–19 號區塊 swap in 回主記憶體。

    3.2.3 Context Switch（內容切換／上下文切換）重點

    • CPU 切換到另一個 process 時，系統必須保存舊 process 的狀態，並載入新 process 先前保存的狀態。這個動作叫 context switch。
    • Context（內容） 記錄在 process 的 PCB 中：CPU 暫存器的值、process state、記憶體管理資訊。
    • Context-switch 的時間是純粹的 overhead（額外負擔）：切換期間系統不做任何有用的工作。
      • 典型速度是幾微秒（microseconds）。
    • 切換時間高度取決於硬體支援。

    CPU 從 P0 切換到 P1 的過程：

       Process P0            Operating System             Process P1
   executing                                            idle
       │      ── interrupt or system call ──►
       ▼           save state into PCB0
     idle                   ⋮
                   reload state from PCB1  ──────────► executing
                                                           │
              ◄── interrupt or system call ──              ▼
                   save state into PCB1                  idle
                            ⋮
   executing ◄──── reload state from PCB0

    補充例子：你同時寫兩科作業。換科目時要把目前的課本收起來、記下寫到第幾題（save），再拿出另一科課本、翻到上次的地方（reload）。這段時間兩科都沒有進度，換得越頻繁浪費越多。

    補充背景：CPU 如何執行指令

    • 投影片例子：8086 微處理器的處理器模型，以及 SIC（Simplified Instructional Computer）——CPU 內有暫存器 A、X、L、PC（program counter）、SW，以及 CU（控制單元）與 ALU（算術邏輯單元）。
    • 執行每道指令的三步驟：1. Fetch（擷取）→ 2. Decode（解碼）→ 3. Execution（執行）。
    • 這些暫存器的內容就是 context switch 時要保存與恢復的東西：OS 為每個 process 維護一個 PCB（存 pc、sp…），切換時把 CPU 暫存器存進舊 PCB，再從新 PCB 載入。

    3.3 行程的操作 (Operations on Processes)

    3.3.1 Process Creation（行程建立）

    OS 建立 process 的步驟（對應狀態 new → ready）：

    1. 配置記憶體
    2. 把程式的 executable image 載入記憶體
    3. 設定 PCB
      • 管理與執行中程式相關的資料結構
      • 設定 CPU context（PC、SP、registers）
      • PC 設為 entry point
    4. 把新 process 放入 ready queue（把它的 PCB 串到 ready queue）

    Process Tree（行程樹）

    • Process 執行時可以建立多個新 process。
    • 建立者稱為 parent process（父行程），被建立的是 child process（子行程）；子行程又可以建立其他 process，形成樹狀結構。
    • Process 通常以 pid（process identifier，行程識別碼） 來識別與管理。

    面向 可能的選擇
    Resource sharing（資源共享） ① parent 與 children 共享所有資源
    ② children 共享 parent 資源的子集合
    ③ parent 與 child 不共享資源
    Execution（執行） ① parent 與 children 並行（concurrently） 執行

    UNIX：fork() 與 exec()重點

    System call 作用
    fork() 建立一個新 process，是 parent 的複製品
    exec() 在 fork() 之後使用，把 process 的記憶體空間換成一個新程式
    wait() parent 等待 child 結束

    fork() 的回傳值——分辨自己是誰的關鍵：

    回傳值 意義
    < 0 fork 失敗
    == 0 我是 child
    > 0 我是 parent，回傳值是 child 的 pid

    投影片例子（Fig. 3.8）：用 fork() 建立獨立的 process

    #include <sys/types.h>
#include <stdio.h>
#include <unistd.h>

int main()
{
    pid_t pid;

    pid = fork();                    /* fork a child process */

    if (pid < 0) {                   /* error occurred */
        printf("Fork Failed");
        exit(-1);
    }
    else if (pid == 0) {             /* child process */
        execlp("/bin/ls", "ls", NULL);
    }
    else {                           /* parent process */
        wait(NULL);                  /* wait for child to complete */
        printf("child complete");
    }
    return 0;
}

    Child 執行的程式碼與 parent 相同，差別只在 fork() 對 child 回傳 0。

    執行流程（Fig. 3.9）：

                            ┌─ parent (pid > 0) ── wait() ─────────────► parent resumes
  parent ── fork() ─────┤                         ▲
                        └─ child (pid = 0) ── exec() ── exit() ──────┘

    從記憶體的角度看（投影片的三張圖）：

    階段 記憶體中的情況
    1. 呼叫 fork() OS 建立 PCB2，並把 process 1 的內容複製成 process 2。兩者程式碼相同
    2. fork() 返回 兩個 process 都從 fork() 之後的下一行繼續執行，各有自己的 pc、sp。Parent 走 else 去 wait()；child 走 if (pid == 0)
    3. Child 呼叫 execve("a") Process 2 的記憶體內容被換成程式 "a"，從頭開始執行。Process 1 不受影響

    補充例子：fork() 像細胞分裂——分裂後有兩個一模一樣的細胞，都記得分裂前的一切，只有「我是原本的還是新的」這件事不同。exec() 則像新細胞把自己的 DNA 整個換掉，變成另一種細胞。

    補充：exec() 成功後不會返回，因為原本的程式碼已經被換掉了。所以寫在 execlp() 後面的程式碼，只有在 exec 失敗時才會執行到。

    3.3.2 Process Termination（行程終止）

    Process 自己結束（exit() system call）：

    • 執行完最後一道敘述，要求 OS 刪除自己。
    • Child 可以回傳一個狀態值（status value） 給 parent（parent 透過 wait() 取得）。
    • Process 的資源由 OS 回收（deallocate）。

    Parent 終止 children（例如 Windows 的 TerminateProcess()），原因可能是：

    • Child 超用了被配置的資源。
    • 指派給 child 的工作不再需要。
    • Parent 要結束，而有些 OS 不允許 parent 終止後 child 繼續存在。
      • 所有 children 都被終止——cascading termination（連鎖終止／層疊式終止）。

    UNIX／Linux 的終止

    pid_t pid;
int status;
pid = wait(&status);    // 等待 child 終止，回傳該 child 的 pid
    名詞 中文 定義 處理方式
    Zombie process 殭屍行程 Process 已經終止，但 parent 還沒呼叫 wait() Parent 呼叫 wait() 後，zombie 的 pid 與 process table 項目才被釋放
    Orphan process 孤兒行程 Parent 先終止了，留下還在執行的 children 把 init process 指定為孤兒的新 parent；init 會定期呼叫 wait()

    補充例子：

    • Zombie：學生考完交卷離開了（已終止），但老師還沒登記成績（parent 沒 wait()），所以座位表上還留著他的名字。
    • Orphan：父母先離開了，孩子由 init（現代 Linux 是 systemd）收養。

    為什麼需要 zombie 這個狀態？因為 child 的結束狀態要留著等 parent 來讀取。

    3.4 行程間通訊 (Interprocess Communication)

    並行執行的 process 分兩種：

    類型 中文 定義
    Independent process 獨立行程 不會影響其他 process，也不受影響
    Cooperating process 合作行程 會影響其他 process 或受其影響；任何與其他 process 共享資料的 process 都是

    需要 cooperating process 的原因：

    原因 中文 說明
    Information sharing 資訊共享 多個應用程式可能需要同一份資訊
    Computation speedup 加速運算 把工作拆成子工作平行執行（需要多個處理核心）
    Modularity 模組化 把系統功能分成獨立的 process

    投影片例子：

    • Producer–consumer：producer process → buffer → consumer process。
    • Parallel computing（平行運算）：兩個 CPU core 各處理 int array[N] 的一半。

    Cooperating process 需要 IPC（Interprocess Communication，行程間通訊） 機制來交換資料。兩種基本模型：

    (1) Shared memory（共享記憶體） (2) Message passing（訊息傳遞）
    做法 建立一塊由合作 process 共享的記憶體區域，透過讀寫該區域交換資訊 透過在合作 process 之間交換訊息來通訊
    是否經過 kernel 只有建立共享區域時需要 system call；建立後所有存取都是一般的記憶體存取，不需 kernel 協助 通常用 system call 實作，每次都需要 kernel 介入
    速度 較快（以記憶體傳輸速度進行） 較慢
    適合 同一台電腦內、大量資料 少量資料（不需避免衝突）
    分散式系統 較難 較容易實作（跨電腦通訊）
    注意事項 需要自行處理 protection 與 synchronization —

    3.5 共享記憶體系統的 IPC

    • 要通訊的 process 必須建立一塊共享記憶體區域。
    • 共享記憶體區域通常位於建立它的 process 的位址空間中。
    • 其他想用它通訊的 process 必須把它 attach（附加） 到自己的位址空間。
    • 使用類似 shared_memory_create() 與 shared_memory_attach() 的 system call。
    • 一般情況 OS 會阻止 process 存取別人的記憶體，所以需要兩個以上的 process 同意移除這項保護限制。
    • 資料的格式與位置由這些 process 決定，不受 OS 控制。
    • Process 也要負責確保不會同時寫入同一位置——需要 protection 與 synchronization（同步問題詳見 Chapter 6、7）。

    Producer–Consumer Problem（生產者–消費者問題）重點

    合作 process 的典範（paradigm）：producer（生產者） process 產生資訊，由 consumer（消費者） process 消耗。

    投影片例子：web server（producer）產生網頁內容，web browser（consumer）讀取。

    兩者之間需要一個 buffer（緩衝區）：

    類型 中文 說明
    Unbounded buffer 無限緩衝區 大小沒有限制。Producer 永遠可以放；consumer 可能要等
    Bounded buffer 有限緩衝區 固定大小。滿了 producer 要等；空了 consumer 要等

    Buffer 可以由 OS 透過 message-passing 設施提供，也可以由程式設計師用 shared memory 自行撰寫。

    Bounded-Buffer 的 Shared-Memory 解法

    共享資料——用環狀陣列（circular array） 實作：

    #define BUFFER_SIZE 10

typedef struct {
    ...
} item;

item buffer[BUFFER_SIZE];
int in = 0;      // 下一個空位（next free position）
int out = 0;     // 第一個有資料的位置（first full position）
    狀態 判斷條件
    Empty（空） in == out
    Full（滿） ((in + 1) % BUFFER_SIZE) == out

    Producer process：

    item next_produced;

while (true) {
    /* produce an item in next_produced */

    while (((in + 1) % BUFFER_SIZE) == out)
        ;   /* do nothing —— buffer 滿了，空轉等待 */

    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}

    Consumer process：

    item next_consumed;

while (true) {
    while (in == out)
        ;   /* do nothing —— buffer 空了，空轉等待 */

    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;

    /* consume the item in next_consumed */
}

    投影片例子：逐步追蹤（BUFFER_SIZE = 10，格子編號 0–9）

    動作 in out 項目數 狀態
    初始 0 0 0 empty（in == out）
    生產 1 個 1 0 1
    再生產 1 個 2 0 2
    持續生產到第 9 個 9 0 9 full（(9+1) % 10 == 0）
    消費 1 個 9 1 8
    再消費 1 個 9 2 7
    生產 1 個（放在格子 9，in 繞回 0） 0 2 8
    再生產 1 個 1 2 9 full（(1+1) % 10 == 2）

    投影片的提問：這個解法正確，但 buffer 最多只能放 BUFFER_SIZE − 1 個項目。為什麼？

    因為只靠 in 和 out 兩個變數來判斷空與滿。如果允許 10 格全部放滿，in 會繞一圈追上 out，變成 in == out——跟「空」的條件一模一樣，無法分辨。所以必須故意留一格不用，讓「滿」的條件變成「in 的下一格是 out」。

    （補充：若想用滿全部 BUFFER_SIZE 格，可以另外加一個計數變數 count 記錄目前項目數；但兩個 process 同時修改 count 會產生同步問題，這是後面章節討論 race condition 的經典例子。）

    3.6 訊息傳遞系統的 IPC

    • Shared memory 的做法要求 process 共享一塊記憶體，且存取與操作的程式碼要由程式設計師明確撰寫。
    • 另一種方式：由 OS 提供 message-passing 設施讓合作 process 通訊。
    • Message passing 讓 process 不需共享同一位址空間就能通訊並同步彼此的動作。
      • 對位於不同電腦上的 process 特別有用。
      • 投影片例子：Internet 聊天程式。

    至少提供兩個操作：

    • send(message)——訊息大小可以固定或可變
    • receive(message)

    若 P 與 Q 要通訊，需要：

    1. 在兩者間建立 communication link（通訊鏈結）
    2. 用 send / receive 交換訊息

    邏輯上實作 link 與 send/receive 的三個面向：

    面向 選擇 章節
    Naming Direct 或 indirect communication 3.6.1
    Synchronization Synchronous 或 asynchronous communication 3.6.2
    Buffering Automatic 或 explicit buffering 3.6.3

    投影片例子：用 message passing 解 producer–consumer 問題

    /* producer */                        /* consumer */
message next_produced;                message next_consumed;

while (true) {                        while (true) {
    /* produce an item in                 receive(&next_consumed);
       next_produced */                   /* consume the item in
    send(next_produced);                     next_consumed */
}                                     }

    比 shared-memory 版本簡單很多——buffer 的管理、滿了要等、空了要等，全部由 OS 處理。

    3.6.1 Naming（命名）

    要通訊的 process 必須有辦法指稱對方。

    Direct Communication（直接通訊）

    Process 必須明確指名對方：

    • send(P, message)——送訊息給 process P
    • receive(Q, message)——從 process Q 接收訊息

    Link 的特性：

    • 每一對想通訊的 process 之間自動建立 link。
    • 一條 link 剛好關聯兩個 process。
    • 每對 process 之間剛好只有一條 link。

    定址方式：

    Sender Receiver
    Symmetric（對稱） send(P, message) receive(Q, message)——指名從 Q 收
    Asymmetric（非對稱） send(P, message) receive(id, message)——從任何 process 收，id 會被設為發送者

    缺點：模組化程度有限。改變某個 process 的識別碼，就得檢查並修改所有其他提到舊識別碼的 process 定義——識別碼被寫死（hard-coded） 在程式裡。

    Indirect Communication（間接通訊）

    • 訊息送到 mailbox（信箱）（也稱 port，埠），並從中接收。
    • 每個 mailbox 有唯一的 id。
    • Process 只有在共享同一個 mailbox 時才能通訊。
    • send(A, message)——送訊息到 mailbox A
    • receive(A, message)——從 mailbox A 接收訊息

    Link 的特性：

    • 只有當一對 process 共享 mailbox 時才建立 link。
    • 一條 link 可以關聯兩個以上的 process。
    • 每對 process 之間可以有多條 link，每條對應一個 mailbox。

    Mailbox sharing 的問題：

    P1、P2、P3 共享 mailbox A。P1 送出訊息，P2 和 P3 都執行 receive——誰收到？

    解法：

    1. 一條 link 最多只關聯兩個 process。
    2. 同一時間最多只允許一個 process 執行 receive。
    3. 讓系統任意選擇接收者，並通知 sender 是誰收到的。

    Mailbox 的擁有者：

    擁有者 說明
    Process Owner：只能從 mailbox 接收訊息。User：只能傳送訊息到 mailbox
    OS OS 必須提供機制讓 process：建立新 mailbox、透過 mailbox 傳送與接收、刪除 mailbox
    Direct Indirect
    指定對象 對方的 process 名稱 mailbox 的 id
    一條 link 關聯 剛好 2 個 process 可以 2 個以上
    每對 process 的 link 數 剛好 1 條 可以多條

    補充例子：Direct 像打電話給特定的人——你必須知道他的號碼，他換號碼你就找不到。Indirect 像寄信到公司的客服信箱——你不需要知道是哪位客服處理，換人了也沒關係。

    3.6.2 Synchronization（同步）

    Message passing 可以是 blocking（阻塞） 或 nonblocking（非阻塞）。

    Blocking（＝ synchronous，同步） Nonblocking（＝ asynchronous，非同步）
    send Sender 被擋住，直到訊息被 receiver 或 mailbox 收到 Sender 送出訊息後繼續執行
    receive Receiver 被擋住，直到有訊息可收 Receiver 立刻取得一則有效訊息，或得到 null
    • 當 send() 與 receive() 都是 blocking 時，sender 與 receiver 之間形成 rendezvous（會合）。

    補充例子：Blocking send 像打電話，要等對方接起來才能講；nonblocking send 像傳 LINE，送出後就去做別的事。Blocking receive 像守在信箱前等信；nonblocking receive 像經過時看一眼，沒信就走。

    3.6.3 Buffering（緩衝）

    附屬於 link 的訊息佇列，有三種實作方式：

    類型 容量 Sender 的行為 分類
    Zero capacity（零容量） 佇列長度 = 0 必須 block，直到 recipient 收下訊息 No buffering
    Bounded capacity（有限容量） 有限長度 n 佇列滿了才要等 Automatic buffering
    Unbounded capacity（無限容量） 無限長度 永遠不會 block Automatic buffering

    3.7 IPC 系統實例

    3.7.1 POSIX Shared Memory

    步驟 函式 說明
    1. 建立共享記憶體區段 shm_fd = shm_open(name, O_CREAT | O_RDWR, 0666); 也用來開啟既有的區段
    2. 設定物件大小 ftruncate(shm_fd, 4096);
    3. 建立 memory-mapped file（記憶體映射檔） ptr = mmap(0, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, shm_fd, 0); 把共享記憶體物件映射到位址空間
    4. 當成一般記憶體存取 sprintf(ptr, "%s", message_0); 用 mmap() 回傳的指標
    5. 從系統移除 shm_unlink(name);

    留意 投影片第 75 頁的說明把旗標寫成 O_RDRW，應為 O_RDWR（read-write）；後面第 76 頁的完整程式碼是正確的。

    投影片例子（Fig. 3.16）：Producer——寫入共享記憶體

    #include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <sys/shm.h>
#include <sys/stat.h>
#include <sys/mman.h>

int main()
{
    const int SIZE = 4096;
    const char *name = "OS";            // name of shared memory object
    const char *message_0 = "Hello";
    const char *message_1 = "World!";
    int fd;                             // shared memory file descriptor
    char *ptr;                          // pointer to shared memory object

    /* create the shared memory object */
    fd = shm_open(name, O_CREAT | O_RDWR, 0666);

    /* configure the size of the shared memory object */
    ftruncate(fd, SIZE);

    /* now map the shared memory object in the address space of the process */
    ptr = (char *) mmap(0, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (ptr == MAP_FAILED) {
        printf("Map failed\n");
        return -1;
    }

    /* write to the shared memory object */
    sprintf(ptr, "%s", message_0);
    ptr += strlen(message_0);
    sprintf(ptr, "%s", message_1);
    ptr += strlen(message_1);

    return 0;
}

    投影片例子（Fig. 3.17）：Consumer——讀取共享記憶體

    #include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <sys/shm.h>
#include <sys/stat.h>
#include <sys/mman.h>

int main()
{
    const char *name = "OS";            // name of shared memory object
    const int SIZE = 4096;
    int fd;                             // shared memory file descriptor
    char *ptr;                          // pointer to shared memory object
    int i;

    /* open the shared memory object */
    fd = shm_open(name, O_RDONLY, 0666);
    if (fd == -1) {
        printf("shared memory failed\n");
        exit(-1);
    }

    /* now map the shared memory object in the address space of the process */
    ptr = (char *) mmap(0, SIZE, PROT_READ, MAP_SHARED, fd, 0);
    if (ptr == MAP_FAILED) {
        printf("Map failed\n");
        exit(-1);
    }

    /* now read from the shared memory object */
    printf("%s", (char *)ptr);

    /* remove the shared memory object */
    if (shm_unlink(name) == -1) {
        printf("Error removing %s\n", name);
        exit(-1);
    }
    return 0;
}

    重點：兩個程式用同一個名稱 "OS" 找到同一塊共享記憶體。Producer 寫入 "Hello" 和 "World!"，consumer 讀出後印出 HelloWorld!，然後移除該區段。

    補充：在 Linux 編譯這類程式，較舊的 glibc 需要加 -lrt（例如 gcc producer.c -o producer -lrt）；程式中用到 ftruncate() 另需 #include <unistd.h>。

    3.7.2 Mach Message Passing

    • Mach kernel 支援建立與銷毀多個 task（類似 process），每個 task 有多個 thread。
    • Mach 中大部分通訊都透過訊息進行。訊息送到 mailbox 並從中接收，mailbox 在 Mach 中稱為 port（埠）。
    • 每個 task 建立時，同時建立兩個 mailbox：
      • Kernel mailbox：kernel 用來與 task 通訊。
      • Notify mailbox：kernel 用來通知事件發生。

    訊息傳輸只需三個 system call：

    System call 作用
    msg_send() 傳送訊息
    msg_receive() 接收訊息
    msg_rpc() 傳送一則訊息，並等待 receiver 剛好一則回覆
    port_allocate() 建立新 mailbox 並配置其訊息佇列的空間

    投影片例子：Mach 訊息的結構與收發

    #include <mach/mach.h>

struct message {
    mach_msg_header_t header;
    int data;
};

mach_port_t client;
mach_port_t server;

    Client 端——送出訊息：

    struct message message;

// construct the header
message.header.msgh_size = sizeof(message);
message.header.msgh_remote_port = server;
message.header.msgh_local_port = client;

// send the message
mach_msg(&message.header,        // message header
         MACH_SEND_MSG,          // sending a message
         sizeof(message),        // size of message sent
         0,                      // maximum size of received message - unnecessary
         MACH_PORT_NULL,         // name of receive port - unnecessary
         MACH_MSG_TIMEOUT_NONE,  // no time outs
         MACH_PORT_NULL);        // no notify port

    Server 端——接收訊息：

    struct message message;

// receive the message
mach_msg(&message.header,        // message header
         MACH_RCV_MSG,           // receiving a message
         0,                      // size of message sent
         sizeof(message),        // maximum size of received message
         server,                 // name of receive port
         MACH_MSG_TIMEOUT_NONE,  // no time outs
         MACH_PORT_NULL);        // no notify port

    同一個函式 mach_msg() 靠第二個參數（MACH_SEND_MSG / MACH_RCV_MSG）決定是送還是收。 留意 投影片 server 端 MACH_RCV_MSG 那行的註解寫的是 "sending a message"，是沿用課本的筆誤，實際意思是接收。

    Send 與 receive 很有彈性：

    • Mailbox 沒滿：訊息被複製進去，sending thread 繼續執行。
    • Mailbox 滿了，sending thread 有四個選擇：
      1. 無限期等待，直到 mailbox 有空間。
      2. 最多等 n 毫秒。
      3. 完全不等，立刻返回。
      4. 暫時快取一則訊息（OS 只多保留一則）。
    • 沒有訊息可收時，receiving thread 可以：等待、最多等 n 毫秒、或不等。

    效能問題與解法：

    • Mach 特別為分散式系統設計，但也適用於處理核心較少的系統。
    • 訊息系統的主要問題是效能差，因為要把訊息從 sender 的 port 複製到 receiver 的 port。
    • Mach 用虛擬記憶體管理技術避免複製：把含有 sender 訊息的位址空間映射（map） 到 receiver 的位址空間，訊息本身從未真正被複製。
      • 只適用於系統內部（intrasystem） 的訊息。
      • 相關技術：copy-on-write、shared memory。

    3.7.3 Windows — ALPC

    • Windows 支援多種操作環境，稱為 subsystem（子系統）。
    • 應用程式透過 message-passing 機制與 subsystem 通訊；應用程式可視為 Windows subsystem server 的 client。
    • Windows 的 message-passing 設施稱為 ALPC（Advanced Local Procedure Call，進階本地程序呼叫）。
    • 只能用於同一系統上的 process 之間。
    • 用 port（類似 mailbox）建立並維護通訊管道。

    通訊流程（Fig. 3.19）：

    步驟 動作
    1 Client 開啟 subsystem 的 connection port 物件的 handle（控制代碼）
    2 Client 送出 connection request（連線請求）
    3 Server 建立兩個私有的 communication port（client communication port 與 server communication port），並把其中一個的 handle 回傳給 client
    4 Client 與 server 用各自的 port handle 傳送訊息或 callback，並監聽回覆

    圖中還有 shared section object（> 256 bytes）： （補充：較小的訊息直接透過 port 的訊息佇列複製；較大的訊息則透過 section object 這塊共享記憶體傳遞，避免複製大量資料。）

    3.7.4 Pipes（管道）

    Pipe 像一條導管（conduit），讓兩個 process 通訊（源自 UNIX）。設計 pipe 時要考慮四個問題：

    1. Unidirectional（單向） 還是 bidirectional（雙向） 通訊？
    2. 若是雙向，是 half duplex（半雙工：同一時間資料只能往一個方向）還是 full duplex（全雙工：資料可同時雙向傳輸）？
    3. 通訊的 process 之間是否必須有 parent–child 關係？
    4. 能否跨網路通訊？

    3.7.4.1 Ordinary Pipes（普通管道）

    • 單向通訊；需要 parent–child 關係。
    • UNIX：用 read() 與 write() system call 存取。
    • Windows：稱為 anonymous pipe（匿名管道），用 ReadFile() 與 WriteFile() 存取。
    • pipe(fd) 建立後：fd[0] 是 read end（讀取端），fd[1] 是 write end（寫入端）。

    投影片例子（Fig. 3.21、3.22）：UNIX 的 ordinary pipe

    #include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <string.h>

#define BUFFER_SIZE 25
#define READ_END    0
#define WRITE_END   1

int main(void)
{
    char write_msg[BUFFER_SIZE] = "Greetings";
    char read_msg[BUFFER_SIZE];
    pid_t pid;
    int fd[2];

    /* create the pipe */
    if (pipe(fd) == -1) {
        fprintf(stderr, "Pipe failed");
        return 1;
    }

    /* fork a child process */
    pid = fork();

    if (pid < 0) {
        fprintf(stderr, "Fork failed");
        return 1;
    }

    if (pid > 0) {   /* parent process */
        /* close the unused end of the pipe */
        close(fd[READ_END]);

        /* write to the pipe */
        write(fd[WRITE_END], write_msg, strlen(write_msg) + 1);

        /* close the write end of the pipe */
        close(fd[WRITE_END]);
    }
    else {           /* child process */
        /* close the unused end of the pipe */
        close(fd[WRITE_END]);

        /* read from the pipe */
        read(fd[READ_END], read_msg, BUFFER_SIZE);
        printf("child read %s\n", read_msg);

        /* close the read end of the pipe */
        close(fd[READ_END]);
    }
    return 0;
}

    流程：先 pipe() 再 fork()，所以 child 繼承了 pipe 的兩端。Parent 關掉讀取端、寫入 "Greetings"；child 關掉寫入端、讀出後印出 child read Greetings。 為什麼要先關掉不用的那一端？ 因為 pipe 是單向的，各自只用一端；也讓讀取方在寫入方關閉後能偵測到 end-of-file。 留意 投影片 child 最後一行的註解寫 "close the write end"，實際關閉的是 read end（fd[READ_END]）。

    補充例子：shell 裡的 ls | grep txt 中的 | 就是 pipe——ls 的輸出接到 grep 的輸入。

    3.7.4.2 Named Pipes（具名管道）

    • 雙向通訊；不需要 parent–child 關係。
    • 建立後多個 process 都可以使用；通訊的 process 結束後它仍然存在。
    UNIX（稱為 FIFO） Windows
    雙工 Half-duplex Full-duplex
    位置 通訊的 process 必須在同一台機器 不必在同一台機器

    Ordinary vs. Named Pipes

    Ordinary pipe Named pipe
    方向 單向 雙向
    Parent–child 關係 需要 不需要
    存在時間 通訊的 process 結束就消失 持續存在，直到被明確刪除

    3.8 主從式系統的通訊

    Shared memory 與 message passing 也能用於 client-server 系統。另外還有兩種策略：Sockets 與 RPC。

    3.8.1 Sockets（通訊端）

    • Socket 定義為通訊的端點（endpoint for communication）。
    • 一對透過網路通訊的 process 使用一對 socket，每個 process 一個。
    • Socket 由 IP address 加上 port number（埠號） 來識別。
    • 通訊發生在一對 socket 之間。
    • 在主機間傳送的封包，依據目的埠號送到正確的 process。

    投影片例子：

    • socket 161.25.19.8:1625 指的是主機 161.25.19.8 上的 port 1625。
    • Host X（146.86.5.20）的 socket 146.86.5.20:1625 ↔ web server（161.25.19.8）的 socket 161.25.19.8:80。

    補充：IP address 像大樓地址，port number 像門牌房號。Server 通常監聽固定的 well-known port（1024 以下，如 HTTP 是 80、SSH 是 22）；client 的 port 由系統指派一個大於 1024 的號碼。

    投影片例子：Java 的 Date Server

    import java.net.*;
import java.io.*;

public class DateServer
{
    public static void main(String[] args) {
        try {
            ServerSocket sock = new ServerSocket(6013);

            // now listen for connections
            while (true) {
                Socket client = sock.accept();
                // we have a connection

                PrintWriter pout = new
                    PrintWriter(client.getOutputStream(), true);

                // write the Date to the socket
                pout.println(new java.util.Date().toString());

                // close the socket and resume listening for more connections
                client.close();
            }
        }
        catch (IOException ioe) {
            System.err.println(ioe);
        }
    }
}

    Date Client：

    import java.net.*;
import java.io.*;

public class DateClient
{
    public static void main(String[] args) {
        try {
            // this could be changed to an IP name or address other than the localhost
            Socket sock = new Socket("127.0.0.1", 6013);

            InputStream in = sock.getInputStream();
            BufferedReader bin = new
                BufferedReader(new InputStreamReader(in));

            String line;
            while ((line = bin.readLine()) != null)
                System.out.println(line);

            sock.close();
        }
        catch (IOException ioe) {
            System.err.println(ioe);
        }
    }
}

    流程：Server 在 port 6013 監聽，accept() 會 block 直到有 client 連線；連上後把目前日期時間寫進 socket 再關閉連線。Client 連到 127.0.0.1:6013（localhost，本機自己），讀出並印出日期。

    3.8.2 Remote Procedure Calls（RPC，遠端程序呼叫）

    • RPC 把網路系統上 process 之間的程序呼叫抽象化。
    • RPC 的語意讓 client 呼叫遠端主機上的程序，就像呼叫本地程序一樣。
    • Stub（存根）：client 端代表 server 上實際程序的 proxy（代理）。
    • Client-side stub：找到 server，並把參數 marshal（封送／打包）。
    • Server-side stub：收到訊息，unmarshal（解開打包的參數），然後在 server 上執行該程序。

    架構：

         Client process                        Server process
   ┌─────────────────┐                   ┌─────────────────┐
   │ Client routines │                   │ Server routines │
   │      ↓  ↑       │                   │      ↓  ↑       │
   │   Client stub   │                   │   Server stub   │
   └──────┬──▲───────┘                   └──────┬──▲───────┘
   ┌──────▼──┴───────┐   ──────────►     ┌──────▼──┴───────┐
   │ network routines│   ◄──────────     │ network routines│
   └─────────────────┘                   └─────────────────┘
       Local kernel                         Remote kernel

    RPC 的執行過程（Fig. 3.29）——client 如何找到 server 的 port：

    步驟 Client 端 訊息內容 Server 端
    1 User 呼叫 kernel，要送 RPC 訊息給程序 X
    2 Kernel 送訊息給 matchmaker（媒合者） 查詢 port From: client／To: server／Port: matchmaker／Re: address for RPC X Matchmaker 收到訊息，查詢答案
    3 Kernel 把 port P 放進使用者的 RPC 訊息 From: server／To: client／Port: kernel／Re: RPC X／Port: P Matchmaker 回覆 client port P
    4 Kernel 送出 RPC From: client／To: server／Port: port P／〈contents〉 監聽 port P 的 daemon 收到訊息
    5 Kernel 收到回覆，傳給 user From: RPC／Port: P／To: client／Port: kernel／〈output〉 Daemon 處理請求並送出輸出

    Matchmaker（也叫 rendezvous daemon）：在固定的 RPC port 上提供查詢服務，告訴 client 某個 RPC 目前在哪個 port。

    補充例子：RPC 像請秘書（client stub）幫你打電話給另一家公司的秘書（server stub），由對方秘書轉告他的老闆（server routine）去做事，再把結果傳回來。你只要像平常交代事情一樣說一聲，不必自己處理撥號、轉接、留言等細節。Marshalling 就是把你的口頭交代整理成對方看得懂的標準格式。

    4.1.1 Motivation（動機）

    現代電腦與行動裝置上的軟體大多是 multithreaded。一個應用程式通常實作成一個獨立的 process，內含數個 thread。

    投影片例子：

    • Web browser（瀏覽器）：一個 thread 顯示圖片或文字，另一個 thread 從網路擷取資料。
    • Word processor（文書處理器）：一個 thread 顯示圖形、一個 thread 回應使用者按鍵、一個 thread 在背景做拼字與文法檢查。
    • 在多核心系統上，應用程式可以把數個 CPU-intensive（CPU 密集） 的工作平行執行。

    Web Server 的三種設計重點

    某些情況下，單一應用程式需要執行數個相似的工作。

        disk read;
        send();

}

    (3) Multithreaded process——每來一個請求就建立一個新 thread：

    void fun() {
    disk read;
    send();
    thread_exit(0);
}

void main() {
    while (1) {

    結論：如果新 process 要做的事和既有 process 相同，讓一個 process 包含多個 thread 通常更有效率。

    4.2 多核心程式設計 (Multicore Programming)

    Multithreaded programming 提供更有效使用多個運算核心的機制，並改善 concurrency（並行）。

    Concurrency vs. Parallelism重點

    Concurrency（並行） Parallelism（平行）
    定義 讓所有工作都能有進展（make progress），支援一個以上的工作 能同時（simultaneously） 執行一個以上的工作
    單核心 可以——thread 的執行隨時間交錯（interleaved） 不行
    多核心 可以 可以——系統把不同 thread 分配到不同 core
    本質 靠 CPU scheduler 快速切換，製造平行的錯覺 真的同時在跑 
     單核心（concurrent, 不是 parallel）：
   core:  T1  T2  T3  T4  T1  T2  T3  T4  T1 ...        → 時間

 雙核心（parallel）：
   core 0:  T1  T3  T1  T3  T1 ...
   core 1:  T2  T4  T2  T4  T2 ...                      → 時間
    • 單處理器／單核心時，process 是 concurrently 執行，但不是 in parallel。
    • 有 concurrency 不一定有 parallelism；有 parallelism 一定有 concurrency。

    投影片例子：四組工作（各拆成 B_0、B_1、B_2、B_3… 等小段）。一顆 CPU 時，四組輪流各執行一小段，總時間長；兩顆 CPU 時，每個時間點有兩組同時執行，總時間明顯縮短。 補充例子：一個人邊煮湯邊切菜，是在兩件事之間來回切換（concurrency）；兩個人一個煮湯一個切菜，是真的同時進行（parallelism）。

    4.2.1 Programming Challenges（程式設計的挑戰）

    多核心系統對兩種人都帶來壓力：

    • OS 設計者：要寫出能利用多核心平行執行的排程演算法。
    • 應用程式設計師：要修改現有程式、設計 multithreaded 程式。

    五大挑戰：

    挑戰 中文 說明
    Dividing activities 劃分活動 找出哪些工作可以平行執行
    Balance 平衡 確保各工作的工作量相當
    Data splitting 資料分割 各工作存取的資料也要切開，才能在不同 core 上執行
    Data dependency 資料相依 若工作之間的資料有相依性，執行必須同步
    Testing and debugging 測試與除錯 平行程式有很多種可能的執行路徑，比單執行緒難測很多

    4.2.2 Types of Parallelism（平行的類型）

    Data parallelism（資料平行） Task parallelism（任務平行）
    分散的是 資料：把同一份資料的子集合分到多個 core 工作（thread）：把不同的 thread 分到多個 core
    各 core 做的事 相同的運算 各自獨特的運算 
     data parallelism：   [ data₀ | data₁ | data₂ | data₃ ]
                         ↓       ↓       ↓       ↓
                       core 0  core 1  core 2  core 3      （資料切開，做同樣的事）

 task parallelism：   [           data             ]
                        ↙      ↓       ↓      ↘
                     core 0  core 1  core 2  core 3        （同一份資料，做不同的事）

    投影片例子：

    • Data parallelism：雙核心系統上兩個 thread 平行加總 int array[N]——thread A 在 core 0 加總 array[0]..[N/2-1]，thread B 在 core 1 加總 array[N/2]..[N-1]。
    • Task parallelism：thread A 做加總、thread B 做相乘；或 producer thread 與 consumer thread。

    4.3 多執行緒模型 (Multithreading Models)

    User Thread 與 Kernel Thread

    User thread（使用者執行緒） Kernel thread（核心執行緒）
    位置 User space，在 kernel 之上 Kernel space
    由誰管理 Thread library（執行緒函式庫），不需 kernel 支援 OS 直接支援與管理
    建立與管理速度 較快（不需要 kernel 介入） 較慢
    • 幾乎所有現代 OS 都支援 kernel thread：Windows、Linux、macOS。

    User-level thread library 的底層可以是什麼（投影片三張圖）：

    情況 Thread library 把 user-level thread 多工在什麼之上
    (1) Kernel 不支援 kernel thread 一個 OS process
    (2) Kernel 支援 kernel thread 一個 kernel thread
    (3) Kernel 支援 kernel thread 一組 kernel thread

    判斷一個模型好壞的兩個問題：

    1. Thread 能否在多核心系統上平行執行？
    2. 一個 thread 呼叫 blocking system call 時，整個 process 是否還能繼續執行？

    三種模型重點

    User thread 與 kernel thread 之間必須有對應關係，常見三種：

    4.3.1 Many-to-One Model（多對一）

    把許多 user-level thread 對應到一個 kernel thread。

      user threads:    ⌇  ⌇  ⌇  ⌇
                    \ |  | /
  kernel thread:       ⌇
    • Thread 管理由 user space 的 thread library 完成，所以有效率。
    • 只要一個 thread 呼叫 blocking system call，整個 process 都會被 block（因為同一時間只有一個 thread 能存取 kernel）。
    • 多個 thread 無法在多核心上平行執行，無法利用多個處理核心。
    • 現在很少系統使用。
    • 投影片例子：Green threads——Solaris 系統的 thread library。

    4.3.2 One-to-One Model（一對一）

    把每個 user thread 對應到一個 kernel thread。

      user threads:    ⌇  ⌇  ⌇  ⌇
                   |  |  |  |
  kernel threads:  ⌇  ⌇  ⌇  ⌇
    • 比 many-to-one 有更多 concurrency：一個 thread 呼叫 blocking system call 時，另一個 thread 可以繼續執行。
    • 允許多個 thread 在多處理器上平行執行。
    • 缺點：建立 user thread 就要建立對應的 kernel thread，大量 kernel thread 可能拖累系統效能。
    • 投影片例子：Linux、Windows 家族。

    4.3.3 Many-to-Many Model（多對多）

    把許多 user-level thread 多工到數量較少或相等的 kernel thread。

      user threads:    ⌇  ⌇  ⌇  ⌇            |user threads| ≥ |kernel threads|
                    \ | / | /
  kernel threads:    ⌇  ⌇  ⌇
    • 開發者可以建立任意多個 user thread，對應的 kernel thread 可在多處理器上平行執行。
    • 一個 thread 執行 blocking system call 時，kernel 可以排程另一個 thread 執行。

    Two-Level Model（二階層模型）

    Many-to-many 的一個變種（variation）：

    • 仍然把許多 user-level thread 多工到較少或相等數量的 kernel thread。
    • 同時允許某個 user-level thread 綁定（bound） 到一個 kernel thread。
    • 看起來最有彈性，但很難實作。

    三種模型比較

    Many-to-One One-to-One Many-to-Many
    可建立的 thread 數 想建多少就多少 要小心不要建太多 想建多少就多少
    多核心上能否 parallel 不行（kernel 一次只能排一個 kernel thread） 可以 可以
    一個 thread block 時 整個 process block 其他 thread 可繼續 其他 thread 可繼續
    缺點 無法利用多核心 kernel thread 數量多，有負擔 難以實作
    例子 Green threads Linux、Windows —

    趨勢：隨著處理核心數量增加，限制 kernel thread 數量已不那麼重要，所以現在大多數 OS 使用 one-to-one model。

    補充例子：把 kernel thread 想成收銀檯、user thread 想成客人。

    • Many-to-one：只有一個收銀檯，一位客人卡住（block），後面全部都動不了。
    • One-to-one：每位客人一個專屬收銀檯，最順，但開太多收銀檯成本很高。
    • Many-to-many：開少數幾個收銀檯讓大家輪流用。

    4.4 執行緒函式庫 (Thread Libraries)

    Thread library（執行緒函式庫）：提供程式設計師建立與管理 thread 的 API。

    兩種主要實作方式：

    (1) User-level library (2) Kernel-level library
    位置 完全在 user space，沒有 kernel 支援 由 OS 直接支援
    程式碼與資料結構 在 user space 在 kernel space
    呼叫函式庫的函式 只是 user space 中的 local function call，不是 system call 會產生對 kernel 的 system call

    目前三個主要的 thread library：

    Library 說明
    POSIX Pthreads POSIX 標準的執行緒延伸；可以實作成 user-level 或 kernel-level library
    Windows Windows 系統上的 kernel-level library
    Java Java thread API 讓 Java 程式直接建立與管理 thread；通常用主機系統上的 thread library 實作（Windows 上用 Windows API；UNIX、Linux、macOS 上用 Pthreads API）

    以下三個例子都做同一件事：用另一個 thread 計算 sum = 1 + 2 + … + N。

    4.4.1 Pthreads

    • Pthreads 指的是 POSIX 標準（IEEE 1003.1c），定義了 thread 建立與同步的 API。
    • 是 specification（規格），不是 implementation（實作）：API 規定 thread library 的行為，怎麼實作由函式庫開發者決定。
    • 常見於 UNIX 類系統：Linux、macOS。

    投影片例子（Fig. 4.11）：使用 Pthread API 的 multithreaded C 程式

    /**
 * 編譯：gcc thrd.c -lpthread      （compile & link with pthread lib.）
 * 執行：a.out <number>
 */
#include <pthread.h>
#include <stdio.h>

int sum;                       /* this data is shared by the thread(s) */

void *runner(void *param);     /* the thread */

main(int argc, char *argv[])
{
    pthread_t tid;             /* the thread identifier */
    pthread_attr_t attr;       /* set of attributes for the thread */

    /* set the default attributes of the thread */
    pthread_attr_init(&attr);

    /* create the thread */
    pthread_create(&tid, &attr, runner, argv[1]);

    /* now wait for the thread to exit */
    pthread_join(tid, NULL);

    printf("sum = %d\n", sum);
}

/* The thread will execute in this function */
void *runner(void *param)
{
    int i, upper = atoi(param);
    sum = 0;

    for (i = 1; i <= upper; i++)
        sum += i;

    pthread_exit(0);
}

    重點函式：

    函式 作用
    pthread_attr_init(&attr) 設定 thread 的預設屬性
    pthread_create(&tid, &attr, runner, argv[1]) 建立 thread。第三個參數是 thread entry function（進入點函式），第四個是傳給它的 argument（參數）
    pthread_join(tid, NULL) 等待該 thread 結束（類似 process 的 wait()）
    pthread_exit(0) Thread 結束自己

    執行過程：程式啟動時只有 main thread。呼叫 pthread_create() 後多了 runner thread，兩者共享全域變數 sum。Main thread 在 pthread_join() 等待；runner 算完並結束後，main 才印出 sum。

    例如執行 a.out 10，輸出 sum = 55。

    • 若 thread 實作有 kernel 支援（例如 Linux 的 one-to-one mapping），pthread_create() 會讓 OS 多建立一個 PCB（PCB2），有自己的 pc、sp，但仍在 process 1 的位址空間內。

    投影片例子（Fig. 4.12）：等待 10 個 thread

    #define NUM_THREADS 10

/* an array of threads to be joined upon */
pthread_t workers[NUM_THREADS];

for (int i = 0; i < NUM_THREADS; i++)
    pthread_join(workers[i], NULL);

    4.4.3 Java Threads

    • Java 在語言層級支援 thread 的建立與管理。
    • Java thread 由 JVM 管理，通常用底層 OS 提供的 thread 模型實作。
    • JVM 規格沒有規定 Java thread 如何對應到底層 OS，由各 JVM 實作決定。層次：Compiled Java program → JVM（Java threads）→ Thread library → Kernel threads。

    建立 Java thread 的兩種方式：

    1. 繼承（extend）Thread 類別
    2. 定義一個實作 Runnable 介面的類別 ← 標準做法

    投影片例子：三個基本動作

    // 實作 Runnable 介面
class Task implements Runnable
{
    public void run() {
        System.out.println("I am a thread.");
    }
}

// 建立 thread

// 等待 thread

    worker.join();

    好處是把「thread 的建立」與「thread 的執行」分開。搭配 Callable 與 Future 還能取得回傳值（Runnable 的 run() 不能回傳結果）：

    投影片例子：

    import java.util.concurrent.*;

class Summation implements Callable<Integer>
{
    private int upper;

    public Summation(int upper) {
        this.upper = upper;
    }

    /* The thread will execute in this method */
    public Integer call() {
        int sum = 0;
        for (int i = 1; i <= upper; i++)
            sum += i;

        return new Integer(sum);
    }
}

public class Driver
{
    public static void main(String[] args) {
        int upper = Integer.parseInt(args[0]);

        ExecutorService pool = Executors.newSingleThreadExecutor();
        Future<Integer> result = pool.submit(new Summation(upper));

        try {
            System.out.println("sum = " + result.get());
        } catch (InterruptedException | ExecutionException ie) { }
    }
}

    submit() 交出工作後立刻拿到一個 Future；result.get() 會等到結果算出來才返回。這樣就不需要前一個例子的 Sum 共享物件，也不用自己呼叫 join()。

    4.5 隱式執行緒 (Implicit Threading)

    Implicit（內含的、隱式的）：

    • Thread 數量增加後，用 explicit thread（明確建立的執行緒） 很難確保程式正確，所以這種做法越來越普遍。
    • Thread 的建立與管理交給 compiler 與 run-time library，而不是程式設計師。
    • 程式設計師只需要指出哪些工作可以平行執行。

    五種方法：Thread Pools、Fork-Join、OpenMP、Grand Central Dispatch、Intel TBB。

    4.5.1 Thread Pools（執行緒池）

    問題：multithreaded server 每收到一個請求就建立一個新 thread。

    • 建立 thread 需要時間。
    • 沒有上限的 thread 可能耗盡系統資源。

    Thread pool 的做法：

    1. Process 啟動時就先建立好一批 thread 放進 pool，讓它們坐著等工作。
    2. Server 收到請求時，從 pool 喚醒一個 thread，把請求交給它。
    3. Thread 完成服務後回到 pool，等下一個工作。

    好處：

    好處 說明
    較快 用現成的 thread 服務請求，比等新 thread 建立好更快
    有上限 限制任一時間存在的 thread 數量
    分離 把「要執行的工作」與「建立工作的機制」分開，可以採用不同的執行策略（例如讓工作週期性執行）

    投影片例子：Windows thread pool API

    DWORD WINAPI PoolFunction(AVOID Param) {
    /*
     * this function runs as a separate thread.
     */
}

QueueUserWorkItem(&PoolFunction, NULL, 0);

    Java 也提供 thread pool 工具（如前面的 Executors）。

    補充例子：餐廳不會每來一桌客人才去招募一位服務生，而是固定雇用幾位，有客人就派一位，服務完回來待命。客人太多時就排隊等，不會無限制加人。

    4.5.2 Fork-Join

    Fork-Join parallelism：多個 thread（工作）被 fork（分出），之後再 join（合併）。

                        ┌─ fork ─► [ task ] ─ join ─┐
   main thread ─────┤                           ├────► main thread
                    └─ fork ─► [ task ] ─ join ─┘

    通用演算法（divide-and-conquer，分治法）：

    Task(problem)
    if problem is small enough
        solve the problem directly
    else
        subtask1 = fork(new Task(subset of problem))
        subtask2 = fork(new Task(subset of problem))

        result1 = join(subtask1)
        result2 = join(subtask2)

        return combined results

    每個 task 可以再 fork 出子 task，形成樹狀結構；子 task 完成後一層層 join 回來。

    投影片例子：Java 的 Fork-Join——加總陣列

    ForkJoinPool pool = new ForkJoinPool();
// array contains the integers to be summed
int[] array = new int[SIZE];

SumTask task = new SumTask(0, SIZE - 1, array);
int sum = pool.invoke(task);

    import java.util.concurrent.*;

public class SumTask extends RecursiveTask<Integer>
{
    static final int THRESHOLD = 1000;

    private int begin;
    private int end;
    private int[] array;

    public SumTask(int begin, int end, int[] array) {
        this.begin = begin;
        this.end = end;
        this.array = array;
    }

    protected Integer compute() {
        if (end - begin < THRESHOLD) {
            int sum = 0;
            for (int i = begin; i <= end; i++)
                sum += array[i];

            return sum;
        }
        else {
            int mid = (begin + end) / 2;

            SumTask leftTask = new SumTask(begin, mid, array);
            SumTask rightTask = new SumTask(mid + 1, end, array);

            leftTask.fork();
            rightTask.fork();

            return rightTask.join() + leftTask.join();
        }
    }
}

    說明：範圍小於 THRESHOLD（1000）就直接加總；否則從中間切成左右兩半，各 fork 一個子 task，再把兩邊 join 回來的結果相加。

    類別 說明
    ForkJoinTask 抽象基底類別
    RecursiveTask 繼承 ForkJoinTask；會回傳結果（透過 compute() 的回傳值）
    RecursiveAction 繼承 ForkJoinTask；不回傳結果

    4.5.3 OpenMP

    • 一組 compiler directive（編譯器指示） 加上 API，支援 C、C++、FORTRAN。
    • 支援共享記憶體環境中的平行程式設計。
    • 標示出 parallel region（平行區域）——可以平行執行的程式碼區塊。
    • 在 Linux、Windows、Mac OS X 的多種開放原始碼與商業 compiler 上都可用。
    指示 作用
    #pragma omp parallel 建立與核心數量一樣多的 thread，各自執行該區塊
    #pragma omp parallel for 把 for 迴圈的各次迭代分給多個 thread 平行執行

    投影片例子：

    #include <omp.h>
#include <stdio.h>

int main(int argc, char *argv[])
{
    /* sequential code */

    #pragma omp parallel
    {
        printf("I am a parallel region.");
    }

    /* sequential code */

    return 0;
}

    在四核心機器上，這行訊息會被印出四次。

    #pragma omp parallel for
for (i = 0; i < N; i++) {
    c[i] = a[i] + b[i];
}

    兩個陣列相加的迴圈被自動拆給多個 thread 平行執行。

    補充：用 gcc 編譯要加 -fopenmp（例如 gcc -fopenmp prog.c），否則 #pragma 會被忽略，程式照樣能跑但只有單一 thread。

    4.5.4 Grand Central Dispatch（GCD）

    • Apple Mac OS X 與 iOS 的技術。
    • 是 C、C++ 語言的延伸，加上 API 與 run-time library。
    • 讓開發者標示出可以平行執行的區段，由 GCD 管理大部分 threading 細節。
    • Block（區塊）：用 ^{ } 包起來的一段獨立工作，例如 ^{ printf("I am a block"); }
    • Block 被放進 dispatch queue（分派佇列）；從佇列取出時，分配給 thread pool 中可用的 thread。

    兩種 dispatch queue：

    類型 取出方式 說明
    Serial（循序） 依 FIFO 順序，一次一個 每個 process 有自己的 serial queue，稱為 main queue（主佇列）；程式設計師可在程式中建立額外的 serial queue
    Concurrent（並行） 依 FIFO 順序，但一次可以取出多個 有三個全系統的佇列，優先權分為 low、default、high

    投影片例子：

    dispatch_queue_t queue = dispatch_get_global_queue
    (DISPATCH_QUEUE_PRIORITY_DEFAULT, 0);

dispatch_async(queue, ^{ printf("I am a block."); });

    取得預設優先權的全域 concurrent queue，再把一個 block 非同步地丟進去執行。

    4.5.5 Intel Threading Building Blocks（TBB）

    • 設計平行 C++ 程式的 template library（樣板函式庫）。

    投影片例子：

    // 循序版本
for (int i = 0; i < n; i++) {
    apply(v[i]);
}

// TBB 的 parallel_for 版本
parallel_for (size_t(0), n, [=](size_t i) { apply(v[i]); });

    開發者只要指出迴圈範圍和每次要做的事，TBB 會自動把迴圈切成數塊並建立工作平行執行。

    五種 Implicit Threading 比較

    方法 平台／語言 核心概念
    Thread pool 通用（Windows API、Java） 預先建立一批 thread 重複使用
    Fork-Join Java 分治法：fork 出子工作，再 join 結果
    OpenMP C、C++、FORTRAN 用 #pragma 標示平行區域
    GCD Apple macOS、iOS 把 block 丟進 dispatch queue
    Intel TBB C++ 樣板函式庫，如 parallel_for

    4.6 執行緒相關議題 (Threading Issues)

    4.6.1 fork() 與 exec() System Calls

    在 multithreaded 程式中，這兩個 system call 的語意改變了。

    fork()：如果程式中的一個 thread 呼叫 fork()，新 process 要複製所有 thread，還是只有呼叫的那一個？

    • 有些 UNIX 系統提供兩種版本的 fork()：
      1. 新 process 複製所有 thread。
      2. 新 process 是 single-threaded（只複製呼叫 fork() 的那個 thread）。

    exec()：如果一個 thread 呼叫 exec()？

    • exec() 參數指定的程式會取代整個 process——包括所有 thread。

    補充：該用哪個版本的 fork()？如果 fork 之後馬上要呼叫 exec()，複製所有 thread 是浪費（反正整個會被換掉），只複製呼叫者就好；如果 fork 之後不呼叫 exec()，新 process 就應該複製所有 thread。

    4.6.2 Signal Handling（訊號處理）

    Signal（訊號）：UNIX 系統中用來通知 process 某個特定事件發生了。

    所有 signal 都遵循同樣的模式：

    1. 某個特定事件發生，產生（generate） signal。
    2. 產生的 signal 被傳遞（deliver） 給 process。
    3. 傳遞後，signal 必須被處理（handle）。
    Synchronous signal（同步訊號） Asynchronous signal（非同步訊號）
    來源 執行中的程式自己的動作造成（即 exception） 執行中 process 外部的事件產生
    例子 非法記憶體存取、除以零 按 Ctrl-C 終止 process、timer 到期
    傳遞對象 傳給造成該 signal 的同一個 process 通常送給另一個 process

    每個 signal 可由兩種 handler 之一處理：

    Handler 中文 說明
    Default signal handler 預設訊號處理常式 Kernel 處理 signal 時執行
    User-defined signal handler 使用者自訂訊號處理常式 可以覆蓋（override） 預設行為

    投影片例子：自訂 signal handler 與傳送 signal

    #include <stdio.h>
#include <signal.h>

void sighup();
void sigint();
void sigquit();

int main(int argc, char *argv[]) {
    int pid;

    if ((pid = fork()) == 0) {
        printf("this is child process for receiving signal\n");
        signal(SIGHUP, sighup);       /* 註冊 user-defined signal handlers */
        signal(SIGINT, sigint);
        signal(SIGQUIT, sigquit);
        for (;;);                     /* 無窮迴圈，等待 signal */
    } else {
        printf("this is parent process for sending signal\n");
        printf("\nPARENT: sending SIGHUP\n\n");
        kill(pid, SIGHUP);            /* sending signals to process */
        printf("\nPARENT: sending SIGINT\n\n");
        kill(pid, SIGINT);
        printf("\nPARENT: sending SIGQUIT\n\n");
        kill(pid, SIGQUIT);
        kill(pid, SIGHUP);
        kill(pid, SIGINT);
    }
}

void sighup() {
    printf("CHILD: I have received a SIGHUP\n");
}

void sigint() {
    printf("CHILD: I have received a SIGINT\n");
}

void sigquit() {
    printf("My DADDY has Killed me!!!\n");
}

    說明：signal(訊號, 函式) 把某個 signal 的處理方式換成自己的函式；kill(pid, 訊號) 把 signal 送給指定的 process（名字叫 kill，但作用是「傳送訊號」，不一定是殺掉）。Child 註冊三個 handler 後空轉等待，parent 依序送出訊號。 補充：實際輸出的順序與次數取決於兩個 process 的執行時機——parent 可能在 child 還沒註冊好 handler 之前就送出 signal，這時會套用預設行為（SIGHUP 的預設動作是終止 process）。

    Multithreaded 環境中 signal 要送給誰？ 四種選擇：

    選擇 適用例子
    1. 送給 signal 所適用的那個 thread Synchronous signal（誰除以零就送給誰）
    2. 送給 process 中的每一個 thread Ctrl-C
    3. 送給 process 中的某些 thread Pthreads 提供 pthread_kill(threadid, signal)
    4. 指定一個特定 thread 接收該 process 的所有 signal Solaris 2

    4.6.3 Thread Cancellation（執行緒取消）

    Thread cancellation：在 thread 完成之前就終止它。被取消的 thread 稱為 target thread（目標執行緒）。

    Asynchronous cancellation（非同步取消） Deferred cancellation（延遲取消）
    做法 一個 thread 立刻終止 target thread Target thread 定期檢查自己是否該終止
    安全性 危險：可能正在更新共享資料、資源可能沒釋放 安全：thread 可以在能安全取消的時間點才結束
    • Pthreads 把這種可以安全取消的點稱為 cancellation point（取消點）。

    投影片例子：Pthread 建立並取消 thread

    pthread_t tid;

/* create the thread */
pthread_create(&tid, 0, worker, NULL);

. . .

/* cancel the thread */
pthread_cancel(tid);

/* wait for the thread to terminate */
pthread_join(tid, NULL);

    呼叫 pthread_cancel() 只是提出取消的請求，實際是否取消取決於 thread 的狀態：

    Mode State Type
    Off Disabled –
    Deferred Enabled Deferred
    Asynchronous Enabled Asynchronous
    • 若 thread 停用（disabled） 取消，請求會保持 pending（擱置），直到 thread 啟用為止。
    • 預設類型是 deferred。
      • 只有當 thread 到達 cancellation point 時才會取消，例如呼叫 pthread_testcancel()。
      • 然後會呼叫 cleanup handler（清理處理常式），讓 thread 在終止前釋放資源。
    • 在 Linux 系統，thread cancellation 是透過 signal 處理的。

    投影片例子：Java 的 thread cancellation Deferred cancellation 使用 interrupt() 方法，它會設定 thread 的 interrupted status（中斷狀態）：

    Thread worker;

. . .

/* set the interruption status of the thread */
worker.interrupt()

    Thread 自己檢查是否被中斷：

    while (!Thread.currentThread().isInterrupted()) {
    . . .
}

    補充例子：Asynchronous 像直接拔掉正在寫入的隨身碟，檔案可能壞掉。Deferred 像按「安全移除」——等它把手上的東西寫完、收拾好才真的停止。瀏覽器載入網頁時按「停止」，就是在取消負責載入的 thread。

    4.6.4 Thread-Local Storage（TLS，執行緒區域儲存）

    • Thread 共享 process 的資料，但有些情況下每個 thread 需要某些資料的自己一份副本，這就是 TLS。
    • 特性：跨函式呼叫都可見（visible across function invocations）。
    • 大多數 thread library（包括 Windows 與 Pthreads）都提供某種 TLS 支援；Java 也有。
    Local variable（區域變數） TLS Global variable（全域變數）
    可見範圍 只在單次函式呼叫期間 跨函式呼叫都可見 整個程式
    每個 thread 一份？ 是（在各自的 stack 上） 是 否（所有 thread 共享）

    補充例子：交易處理系統中，每個 thread 處理一筆交易，需要各自記住「我正在處理的交易編號」。這個值要在該 thread 呼叫的許多函式中都能讀到（所以不能是區域變數），又不能被其他 thread 看到或改到（所以不能是全域變數）。C 語言中的 errno 也是典型例子。

    4.6.5 Scheduler Activations（排程器啟動）

    • 處理的是 kernel 與 thread library 之間的溝通。
    • Many-to-many 與 two-level 模型都需要這種溝通，才能維持配置給應用程式的 kernel thread 數量適當。
    • 通常在 user thread 與 kernel thread 之間使用一個中間資料結構——LWP（Lightweight Process，輕量級行程）。
       user thread      ⌇
                    │
                 ┌─────┐
                 │ LWP │      ← 介於 user-level 與 kernel-level thread 之間
                 └─────┘
                    │
   kernel thread    ⌇
    • 對 user-thread library 而言，LWP 看起來像一個 virtual processor（虛擬處理器），應用程式可以把 user thread 排到上面執行。
    • 每個 LWP 都附屬於一個 kernel thread。

    Upcall（向上呼叫）：

    • Scheduler activation 提供 upcall——一種從 kernel 到 thread library 的溝通機制（方向與 system call 相反）。
    • Upcall 由 thread library 中的 upcall handler 處理。
    • 這種溝通讓應用程式能維持正確數量的 kernel thread。

    補充例子：某個 user thread 即將 block 時，kernel 發 upcall 通知 thread library「這個 thread 要停了」，並配一個新的 LWP 給它，讓 library 可以安排其他 user thread 上去執行，不浪費 CPU。

    4.7 作業系統實例

    4.7.1 Windows Threads

    • Windows 實作 Windows API。
    • Windows 應用程式以獨立的 process 執行，每個 process 可包含一或多個 thread。
    • 採用 one-to-one mapping：每個 user-level thread 對應一個 kernel thread。

    每個 thread 包含：

    • Thread ID
    • Register set：代表處理器的狀態
    • 分開的 user stack 與 kernel stack：分別在 thread 執行於 user mode 與 kernel mode 時使用
    • Private data storage area（私有資料儲存區）：供 run-time library 與 DLL 使用

    Register set、stacks、private storage area 合稱為 thread 的 context。

    Thread 的主要資料結構重點：

    結構 全名 位置 內容
    ETHREAD Executive thread block（執行體執行緒區塊） Kernel space thread start address（起始位址）、指向 parent process 的指標、指向 KTHREAD 的指標
    KTHREAD Kernel thread block（核心執行緒區塊） Kernel space scheduling and synchronization information（排程與同步資訊）、kernel stack、指向 TEB 的指標
    TEB Thread environment block（執行緒環境區塊） User space thread identifier、user stack、thread-local storage 
       kernel space                                    │  user space
   ETHREAD ─────────► KTHREAD ─────────────────────┼──► TEB
   · thread start       · scheduling &             │    · thread identifier
     address              synchronization info     │    · user stack
   · pointer to         · kernel stack             │    · thread-local storage
     parent process                                │

    4.7.2 Linux Threads

    • Linux 不區分 process 與 thread。
      • Linux 通常用 task（任務） 這個詞來指程式中的控制流程，而不說 process 或 thread。
    • Thread 的建立透過 clone() system call。
    • clone() 讓 child task 共享 parent task 的位址空間。
      • 傳入的 flag（旗標） 決定 parent 與 child 之間共享多少。
    Flag 意義
    CLONE_FS 共享檔案系統資訊
    CLONE_VM 共享同一個記憶體空間
    CLONE_SIGHAND 共享 signal handler
    CLONE_FILES 共享已開啟的檔案

    補充：這四個 flag 全部帶上，新 task 幾乎什麼都和 parent 共享，行為就等於一個 thread；一個 flag 都不帶，什麼都不共享，行為就類似 fork() 建立的 process。所以在 Linux 中 process 與 thread 只是「共享程度」不同的 task。這也是 Ch3 提到的 task_struct 同時用來表示兩者的原因。

    5.1 基本概念 (Basic Concepts)

    • Multiprogramming 的目的是取得最大的 CPU 使用率。
    • 幾乎所有電腦資源在使用前都要經過排程。
    • CPU scheduling 是 OS 設計的核心。

    5.1.1 CPU–I/O Burst Cycle（CPU–I/O 爆發週期）

    Process 的執行是由 CPU execution（CPU 執行） 與 I/O wait（I/O 等待） 交替組成的循環（Fig. 5.1）。

       load store
   add store          ┐
   read from file     ┘ CPU burst
   ── wait for I/O ──   I/O burst
   store increment    ┐
   index              │ CPU burst
   write to file      ┘
   ── wait for I/O ──   I/O burst
   load store
   add store          ┐ CPU burst
   read from file     ┘
   ── wait for I/O ──   I/O burst
          ⋮
    名詞 中文 說明
    CPU burst CPU 爆發 一段連續使用 CPU 的時間
    I/O burst I/O 爆發 一段等待 I/O 完成的時間

    CPU burst 的分布（Fig. 5.2）：橫軸是 burst 長度（毫秒），縱軸是出現頻率。曲線顯示大量的短 burst、少量的長 burst。

    類型 中文 特徵
    I/O-bound program I/O 密集型程式 有很多短的 CPU burst
    CPU-bound program CPU 密集型程式 可能有少數幾個長的 CPU burst

    補充例子：文書編輯器是 I/O-bound——大部分時間在等你按鍵，按一下只需要極短的 CPU 時間處理。影片轉檔是 CPU-bound——一直在算，很少等 I/O。

    5.1.2 CPU Scheduler（CPU 排程器）

    • 每當 CPU 閒置（idle），OS 必須從 ready queue 中選出一個 process 來執行。
    • 這個選擇工作由 CPU scheduler 執行。
    • Ready queue 可以用 FIFO queue、priority queue（優先權佇列）、tree（樹） 或 unordered linked list（無序鏈結串列） 實作。

    補充：Ready queue 不一定是「先進先出」的佇列。它裡面放的是各 process 的 PCB，用什麼資料結構、怎麼挑，取決於排程演算法。

    5.1.3 Preemptive & Nonpreemptive Scheduling（可搶占與不可搶占排程）重點

    CPU 排程決策可能在 process 發生下列情況時進行：

    編號 狀態轉換 對應 Ch3 狀態圖
    (0) new → ready admitted
    (1) running → waiting I/O or event wait
    (2) running → ready interrupt
    (3) waiting → ready I/O or event completion
    (4) terminates exit
    • 如果只在 (1) 與 (4) 這兩種情況才排程，稱為 nonpreemptive（不可搶占） 或 cooperative（合作式）。
    • 其他情況也會排程，就是 preemptive（可搶占）。

    投影片例子：在 process state diagram 上標出排程點——preemptive 是 (0, 1, 2, 3, 4) 全部；nonpreemptive 只有圈起來的 (1) 和 (4)。

    為什麼 (1) 和 (4) 一定要排程？因為這兩種情況下目前的 process 自己放棄了 CPU（去等 I/O 或結束了），CPU 空出來，非選下一個不可。其他情況是「目前的 process 還能跑，要不要把它換掉」，只有 preemptive 才會這樣做。

    Nonpreemptive Scheduling（不可搶占排程）

    • CPU 一旦分配給某個 process，該 process 就一直持有 CPU，直到它終止或切換到 waiting 狀態才釋放。
    • 幾乎所有現代 OS 都使用 preemptive 排程演算法：Windows、macOS、Linux、UNIX…

    Preemptive Scheduling（可搶占排程）的問題

    問題 說明 處理方式
    Race condition（競爭條件） 存取共享資料時，一個 process 改到一半被搶走，另一個 process 讀到不一致的資料 需要協調共享資料存取的機制（Chapter 6）
    影響 kernel 設計：在 kernel mode 被搶占 Process 執行 system call 期間被搶占，kernel 資料結構可能不一致 Kernel 在處理 system call 期間不搶占該 process，確保 kernel 結構一致
    影響 kernel 設計：重要 OS 活動中發生中斷 被中斷影響的程式碼必須防止同時被使用 進入時關閉中斷（disable INTs），離開時重新開啟（reenable INTs）

    補充例子（race condition）：兩個 process 共用一個計數器 count = 5。A 讀出 5，正要寫回 6 時被搶占；B 也讀出 5、寫回 6。A 回來後寫回 6。兩次加一，結果卻只多了 1。

    5.2 排程準則 (Scheduling Criteria)

    用來比較 CPU 排程演算法的準則：

    準則 中文 定義 目標
    CPU utilization CPU 使用率 CPU 有多忙。例如 40%（輕負載）到 90%（重負載） 最大化
    Throughput 產能 單位時間內完成的 process 數。例如長 process 每小時 1 個；短交易每秒 10 個 最大化
    Turnaround time 回復時間／周轉時間 執行一個 process 所需的時間，即從送出（submission）到完成（completion） 的間隔 最小化
    Waiting time 等待時間 process 在 ready queue 中等待的總時間 最小化
    Response time 回應時間 從送出請求到產生第一個回應的時間。指的是「開始回應」所需的時間，而不是輸出完整回應的時間 最小化

    最佳化目標（Optimization Criteria）：

    • Max CPU utilization、Max throughput
    • Min turnaround time、Min waiting time、Min response time
    • Min 最大回應時間（minimize the max response time）
    • Min 回應時間的變異數（minimize the variance in the response time）

    本章計算時的常用公式重點（補充整理）：

    Turnaround time = Completion time − Arrival time

                = Completion time − Arrival time − Burst time

    5.3.1 First-Come, First-Served（FCFS，先到先服務）

    誰先到 ready queue，誰就先用 CPU。用 FIFO queue 就能實作。

    投影片例子 1：三個 process 依 P1、P2、P3 的順序到達（皆在時間 0）

    Process Burst Time
    P1 24
    P2 3
    P3 3 
    Gantt chart:
|            P1            | P2 | P3 |
0                         24   27   30
    • Waiting time：P1 = 0，P2 = 24，P3 = 27
    • 平均等待時間 = (0 + 24 + 27) / 3 = 17

    投影片例子 2：同樣三個 process，到達順序改成 P2、P3、P1

    Gantt chart:
| P2 | P3 |            P1            |
0    3    6                         30
    • Waiting time：P1 = 6，P2 = 0，P3 = 3
    • 平均等待時間 = (6 + 0 + 3) / 3 = 3——比上一種情況好很多

    FCFS 的特性：

    • 平均等待時間通常不是最佳的，而且當各 process 的 CPU burst 長度差異很大時，變動也很大。
    • Nonpreemptive：對 time-sharing 系統來說很麻煩（一個 process 可能霸佔 CPU 很久）。

    Convoy effect（護送效應）重點：

    • 短的 process 排在長的 process 後面。
    • 所有其他 process 都在等那個大 process 離開 CPU。
    • 結果使 CPU 與裝置的使用率都降低。

    投影片例子：假設有一個 CPU-bound process 和許多 I/O-bound process。

    1. CPU-bound process 佔著 CPU；I/O-bound process 都做完 I/O 回到 ready queue 排在它後面 → I/O 裝置閒置。
    2. CPU-bound process 終於去做 I/O；I/O-bound process 很快地用完各自短短的 CPU burst，又都去排 I/O，排在 CPU-bound process 後面 → CPU 閒置。
    3. 如此反覆，CPU 和裝置輪流閒著。

    補充例子：超市只有一個收銀台，前面的人推了滿滿一車，後面只買一瓶水的人全部卡住。

    5.3.2 Shortest-Job-First（SJF，最短工作優先）

    • 更精確的名稱是 shortest-next-CPU-burst algorithm（最短下一次 CPU burst 演算法）。
    • 每個 process 都關聯到它下一次 CPU burst 的長度；選擇下一次 CPU burst 最短的 process。
      • 長度相同時，依 FCFS 順序。
    • 看的是 process 下一次 CPU burst 的長度，不是它的總長度。

    兩種版本：

    Nonpreemptive SJF Preemptive SJF ＝ SRTF
    規則 CPU 一旦給了某個 process，在它完成這次 CPU burst 之前不能被搶占 新到達的 process 的 CPU burst 長度小於目前執行中 process 的剩餘時間，就搶占
    全名 — Shortest-Remaining-Time-First（最短剩餘時間優先）

    投影片例子 1：Nonpreemptive SJF（全部在時間 0 到達）

    Process Burst Time
    P1 6
    P2 8
    P3 7
    P4 3 
    | P4 |   P1   |    P3    |    P2    |
0    3        9         16         24

    平均等待時間 = (3 + 16 + 9 + 0) / 4 = 7

    （補充：同樣這四個 process 用 FCFS 的話，平均等待時間是 (0 + 6 + 14 + 21) / 4 = 10.25。）

    投影片例子 2：Nonpreemptive SJF，加入不同的到達時間

    Process Arrival Time Burst Time
    P1 0 7
    P2 2 4
    P3 4 1
    P4 5 4 
    |      P1      | P3 |   P2   |   P4   |
0              7    8       12       16
    • 時間 0 只有 P1，先執行；nonpreemptive，所以 P1 跑完整個 burst（到 7）。
    • 時間 7：P2（4）、P3（1）、P4（4）都到了，選最短的 P3。
    • 時間 8：P2 與 P4 一樣長（4），依 FCFS 選先到的 P2。
    Process 等待時間
    P1 0
    P2 8 − 2 = 6
    P3 7 − 4 = 3
    P4 12 − 5 = 7

    平均等待時間 = (0 + 6 + 3 + 7) / 4 = 4

    投影片例子 3：SRTF（preemptive SJF）

    Process Arrival Time Burst Time
    P1 0 8
    P2 1 4
    P3 2 9
    P4 3 5 
    | P1 |   P2   |    P4    |      P1      |       P3       |
0    1        5         10             17               26
    • 時間 1：P2 到達（4）< P1 剩下的 7 → 搶占，換 P2。
    • 時間 5：P2 完成；剩 P1（7）、P3（9）、P4（5）→ 選 P4。
    • 時間 10：P4 完成；P1（7）< P3（9）→ 選 P1。

    平均等待時間 = [(10 − 1) + (1 − 1) + (17 − 2) + (5 − 3)] / 4 = 26 / 4 = 6.5 ms

    （P1 從時間 1 停到 10 才繼續，所以等了 10 − 1 = 9。）

    投影片例子 4：Preemptive SJF，與例子 2 同一組資料

    Process Arrival Time Burst Time
    P1 0 7
    P2 2 4
    P3 4 1
    P4 5 4 
    |  P1  |  P2  | P3 |  P2  |    P4    |      P1      |
0      2      4    5      7         11             16
    • 時間 2：P2 到達（4）< P1 剩下的 5 → 搶占。
    • 時間 4：P3 到達（1）< P2 剩下的 2 → 搶占。
    • 時間 5：P3 完成；P2 剩 2、P4 為 4、P1 剩 5 → P2。
    • 時間 7：P2 完成；P4（4）< P1（5）→ P4。
    • 時間 11：P4 完成 → P1 跑完。

    用公式 Waiting = Completion − Arrival − Burst：

    Process Completion Arrival Burst Waiting
    P1 16 0 7 9
    P2 7 2 4 1
    P3 5 4 1 0
    P4 11 5 4 2

    平均等待時間 = (9 + 1 + 0 + 2) / 4 = 3（比 nonpreemptive 版本的 4 更好）

    SJF 的優缺點：

    • SJF 可證明是最佳的（provably optimal）：對一組給定的 process，它的平均等待時間最小。
    • 常用於 long-term scheduling（長期排程）。
    • 無法直接用在 short-term scheduling（短期排程，即 CPU 排程）——因為無法事先知道下一次 CPU burst 有多長。
    • 只能預測（predict） 長度：選預測的 CPU burst 最短的 process，來近似 SJF。

    補充：為什麼 SJF 最佳？把短的工作移到長的前面，短工作少等的時間比長工作多等的時間還多，所以總等待時間一定下降。

    預測下一次 CPU burst 的長度重點

    用過去 CPU burst 實際長度的 exponential average（指數平均） 來預測：

    τ(n+1) = α · t(n) + (1 − α) · τ(n)        0 ≤ α ≤ 1
    符號 意義
    t(n) 第 n 次 CPU burst 的實際長度
    τ(n) 對第 n 次 CPU burst 的預測值（代表過去的歷史）
    τ(n+1) 對下一次 CPU burst 的預測值
    α 權重：決定最近一次實際值與過去歷史各佔多少

    投影片例子：α = 1/2，τ0 = 10

    i 0 1 2 3 4 5 6 7
    實際 CPU burst t(i) 6 4 6 4 13 13 13 …
    預測 τ(i) 10 8 6 6 5 9 11 12

    計算過程：

    • τ1 = ½ × 6 + ½ × 10 = 8
    • τ2 = ½ × 4 + ½ × 8 = 6
    • τ3 = ½ × 6 + ½ × 6 = 6
    • τ4 = ½ × 4 + ½ × 6 = 5
    • τ5 = ½ × 13 + ½ × 5 = 9
    • τ6 = ½ × 13 + ½ × 9 = 11
    • τ7 = ½ × 13 + ½ × 11 = 12

    實際值從 4 跳到 13 之後，預測值逐步追上去（5 → 9 → 11 → 12）。

    α 的兩個極端：

    α 公式 意義
    α = 0 τ(n+1) = τ(n) 最近的實際值不算數，預測永遠不變
    α = 1 τ(n+1) = t(n) 只看最後一次實際 CPU burst，過去的歷史不算數

    展開公式：

    τ(n+1) = α·t(n) + (1−α)·α·t(n−1) + … + (1−α)^j·α·t(n−j) + … + (1−α)^(n+1)·τ0

    因為 α 和 (1 − α) 都 ≤ 1，越久以前的 burst 權重越小。

    補充例子：像天氣預報結合「昨天的實際溫度」和「之前的預報」。α 越大，越相信最近發生的事。

    5.3.3 Round-Robin（RR，輪流排程）

    • 專為 time-sharing 系統設計。
    • 每個 process 拿到一小段 CPU 時間，稱為 time quantum（時間配額） 或 time slice（時間片），通常 10 到 100 毫秒。
    • Time quantum 到期（expired） 時，process 就被搶占。
    • Ready queue 維持為 FIFO queue：
      • 新 process 加到尾端（tail）
      • 排程頭端（head） 的第一個 process 執行
      • Timer 響時，執行中的 process 被搶占並加到尾端

    RR 的性質：

    • 若 ready queue 有 n 個 process，time quantum 為 q：
      • 每個 process 每 n·q 個時間單位得到一段 q 的 CPU 時間，也就是每 q 個時間單位得到 1/n 的 CPU。
      • 每個 process 最多等待 (n − 1) × q 個時間單位。
    • RR 的效能取決於 q：
      • q → ∞：RR 變成 FCFS。
      • q 越小：context switch 次數越多。
    • Time quantum 相對於 context-switch 時間必須夠大，但也不能太大。

    12 0
    6 1
    1 9
    • q 應該遠大於 context switch 的時間。
    • q 通常 10 ms 到 100 ms，context switch < 10 μs。

    5.3.4 Priority Scheduling（優先權排程）

    • 每個 process 關聯一個 priority number（優先權數字，整數）。
    • 選擇優先權最高的 process。
    • 優先權相同時，依 FCFS 順序。

    優先權的定義方式：

    類型 中文 例子
    External priority 外部優先權 由系統外部決定：重要性、政治因素…
    Internal priority 內部優先權 用可量測的數值計算：時間限制、記憶體需求、開啟檔案數…
    • SJF 其實是 priority 演算法的一種：優先權就是預測的下一次 CPU burst 時間；CPU burst 越長，優先權越低。

    可搶占或不可搶占：

    新到達的 process 優先權較高時
    Preemptive priority 搶占 CPU
    Nonpreemptive priority 把新 process 放到 ready queue 的頭端（等目前的跑完）

    投影片例子 1：Nonpreemptive priority（全部在時間 0 依 P1…P5 順序到達；數字越小優先權越高）

    P2 1 1
    P3 2 4

    主要問題：Indefinite blocking（無限期阻塞）＝ Starvation（飢餓）重點

    • 低優先權的 process 可能永遠不會被執行。
    • 一個 ready 但一直等不到 CPU 的 process，可以視為被 block 住。

    解法：Aging（老化）

    • 對在系統中等待很久的 process，逐步提高它的優先權。

    補充例子：醫院急診依傷勢輕重（優先權）看診，扭到腳的人可能一直被更急的病人插隊（starvation）。Aging 就像規定「每等 30 分鐘就往前升一級」，最後一定輪得到。

    5.3.5 Multilevel Queue Scheduling（多層佇列排程）

    • 把 process 分成不同群組，因為不同群組可能有不同的排程需求。
      • 例如：foreground（前景，互動式） process 與 background（背景，批次） process。
    • 把 ready queue 分割成多個獨立的佇列：
      • Process 永久（permanently） 被指派到某一個佇列。
      • 每個佇列有自己的排程演算法，例如 foreground 用 RR、background 用 FCFS。

    投影片例子：每個優先權各有一個佇列（Fig. 5.7）

    priority = 0  : T0  T1  T2  T3  T4
priority = 1  : T5  T6  T7
priority = 2  : T8  T9  T10 T11
     ⋮
priority = n  : Tx  Ty  Tz

    佇列之間如何排程（兩種方式）：

    方式 說明
    Fixed-priority preemptive scheduling（固定優先權可搶占） 每個佇列對較低優先權的佇列有絕對優先權；較高優先權的佇列全部空了，較低的才能執行；有新的高優先權 process 進來，就搶占目前的。可能造成 starvation
    Time slice among the queues（佇列間分配時間片） 每個佇列分到一定比例的 CPU 時間，再分給佇列內的 process。例如 80% 給 foreground（RR）、20% 給 background（FCFS）

    投影片例子：四個佇列，由高到低

    最高優先權  ── real-time processes
            ── system processes
            ── interactive processes
最低優先權  ── batch processes

    採用 fixed-priority preemptive 時，batch 佇列中的 process 必須等上面三個佇列全部空了才能執行。

    5.3.6 Multilevel Feedback Queue Scheduling（多層回饋佇列排程）重點

    • 最通用（most general）、也最複雜的 CPU 排程演算法。
    • Process 可以在各佇列之間移動（沒有永久固定的優先權）。
      • 依 CPU burst 的特性把 process 分開。
    • 用 aging 防止 starvation：
      • 用了太多 CPU 時間 → 移到較低優先權的佇列。
      • 在佇列中等太久 → 移到較高優先權的佇列。

    投影片例子：三個佇列

     新工作 ──► [ Q0：quantum = 8  ] ──► 8 ms 內做完就離開
                   │ 沒做完
                   ▼
            [ Q1：quantum = 16 ] ──► 再給 16 ms 內做完就離開
                   │ 還沒做完
                   ▼
            [ Q2：FCFS         ] ──► 做完離開
    • 新工作進入 Q0（Q0 內以 FCFS 服務）。拿到 CPU 時得到 8 ms；8 ms 內沒做完就移到 Q1。
    • 在 Q1 同樣以 FCFS 服務，再得到 16 ms；還是沒做完就被搶占，移到 Q2。
    • Q2 用 FCFS。
    • 效果：CPU burst ≤ 8 ms 的 process 得到最高優先權——它們很快拿到 CPU、做完 burst 就去做 I/O。

    補充：只有 Q0 空了才會執行 Q1，Q0 和 Q1 都空了才會執行 Q2。所以短的、互動式的 process 自然留在上層，CPU-bound 的長工作沉到下層。

    定義一個 multilevel feedback queue scheduler 的參數：

    1. 佇列的數量
    2. 每個佇列的排程演算法
    3. 決定何時把 process 升級（upgrade） 的方法
    4. 決定何時把 process 降級（demote） 的方法
    5. 決定 process 需要服務時進入哪一個佇列的方法
    Multilevel Queue Multilevel Feedback Queue
    Process 能否換佇列 不能，永久指派 可以，依行為升降
    Starvation 可能（fixed-priority 時） 用 aging 防止
    彈性 較低 最高，但最複雜

    5.4 執行緒排程 (Thread Scheduling)

    • 在同時支援 user-level 與 kernel-level thread 的 OS 上，被 OS 排程的是 kernel-level thread。
    • User-level thread 要在 CPU 上執行，最終必須對應到一個 kernel-level thread。
    PCS：Process-Contention Scope（行程競爭範圍） SCS：System-Contention Scope（系統競爭範圍）
    誰在排程 Thread library 把 user-level thread 排到可用的 LWP 上 Kernel 把 kernel thread 排到可用的 CPU 上
    競爭對象 同一個 process 內的 thread 互相競爭 整個系統中所有 thread 互相競爭
    適用模型 Many-to-one、many-to-many 所有模型；one-to-one 只用 SCS
    • 採用 one-to-one 模型的系統（Windows、Linux、Solaris）只用 SCS 排程 thread。
    • POSIX Pthread API 允許在建立 thread 時指定 PCS 或 SCS：
      • PTHREAD_SCOPE_PROCESS：用 PCS 排程
      • PTHREAD_SCOPE_SYSTEM：用 SCS 排程
    • 可能受 OS 限制：Linux 與 Mac OS X 只允許 PTHREAD_SCOPE_SYSTEM。

    投影片例子（Fig. 5.10）：Pthread scheduling API

    #include <pthread.h>
#include <stdio.h>
#define NUM_THREADS 5

int main(int argc, char *argv[])
{
    int i, scope;
    pthread_t tid[NUM_THREADS];
    pthread_attr_t attr;

    /* get the default attributes */
    pthread_attr_init(&attr);

    /* first inquire on the current scope */
    if (pthread_attr_getscope(&attr, &scope) != 0)
        fprintf(stderr, "Unable to get scheduling scope\n");
    else {
        if (scope == PTHREAD_SCOPE_PROCESS)
            printf("PTHREAD_SCOPE_PROCESS");
        else if (scope == PTHREAD_SCOPE_SYSTEM)
            printf("PTHREAD_SCOPE_SYSTEM");
        else
            fprintf(stderr, "Illegal scope value.\n");
    }

    /* set the scheduling algorithm to PROCESS or SYSTEM */
    pthread_attr_setscope(&attr, PTHREAD_SCOPE_SYSTEM);

    /* create the threads */
    for (i = 0; i < NUM_THREADS; i++)
        pthread_create(&tid[i], &attr, runner, NULL);

    /* now join on each thread */
    for (i = 0; i < NUM_THREADS; i++)
        pthread_join(tid[i], NULL);
}

/* Each thread will begin control in this function */
void *runner(void *param)
{
    printf("I am a thread\n");
    pthread_exit(0);
}

    程式先用 pthread_attr_getscope() 查詢目前的競爭範圍，再用 pthread_attr_setscope() 設成 SCS，然後建立 5 個 thread。 留意 投影片程式中用到的 scope 變數沒有宣告，NUM THREADS、pthread t、pthread attr t 也少了底線，上面已補正（int i, scope;、NUM_THREADS、pthread_t、pthread_attr_t）。實際編譯時 runner 也需要先宣告原型。

    5.5 多處理器排程 (Multiple-Processor Scheduling)

    • 有多個 CPU 時，CPU 排程變得更複雜。
    • 多個 CPU 讓 load sharing（負載分擔） 成為可能。
    Homogeneous（同質性） Heterogeneous（異質性）
    處理器 功能完全相同 能力不同
    排程 可以用任何可用的處理器執行佇列中的任何 process 受限於各處理器的能力

    5.5.1 多處理器排程的方法

    Asymmetric multiprocessing（非對稱式） Symmetric multiprocessing, SMP（對稱式）
    做法 所有系統活動由一個特定處理器處理，稱為 master server（主伺服器）；其他處理器只執行 user code 每個處理器自己排程（self-scheduling）
    優點 只有一個處理器存取系統資料結構，減少資料共享的需要 沒有單一處理器的瓶頸
    Ready queue — 可以是共用的 ready queue，或每個處理器各自私有的 ready queue
    使用 — 幾乎所有現代 OS：Windows、Linux、macOS、Android、iOS

    Ready queue 的兩種組織方式：

     (a) 共用 ready queue                 (b) 每個處理器私有 ready queue
     ┌──────────────────┐                core0 ◄── [ T T T ]
     │  T  T  T  T  T   │──► core0        core1 ◄── [ T T ]
     └──────────────────┘──► core1          ⋮
                         ──► …           coren ◄── [ T T T T ]
                         ──► coren

    補充：共用佇列可能有 race condition（兩個 core 同時搶同一個 thread），需要鎖保護；私有佇列沒有這個問題，也比較能利用 cache，是大多數 SMP 系統的做法，但需要 load balancing。

    5.5.2 Multicore Processors（多核心處理器）

    • 近年的趨勢：把多個處理器核心放在同一顆實體晶片上。
      • 對 OS 而言，每個核心看起來就像一個獨立的實體處理器。
      • 比每個處理器各自一顆晶片更快、更省電。
    • Memory stall（記憶體停滯）：處理器存取記憶體時，花大量時間等資料可用（例如發生 cache miss）。

    Multithreaded multicore system（Fig. 5.13）：

    • 每個核心有多個 hardware thread（硬體執行緒） 的設計也越來越多。
      • Multithreaded processor core：每個核心分配兩個以上的 hardware thread。
      • 利用 memory stall 的空檔：一個 thread 在等記憶體時，讓另一個 thread 繼續執行。
      • 對 OS 而言，每個 hardware thread 都是一個 logical processor（邏輯處理器），可以執行一個 software thread。
      • Dual-threaded、dual-core 的系統，OS 看到 4 個 logical processor。
     thread1:       | C | M | C | M | C | M | C |
 thread0:   | C | M | C | M | C | M | C |
            ─────────────────────────────────► time
 C = compute cycle（運算）  M = memory stall cycle（等記憶體）
 一個 thread 在 M 時，核心去執行另一個 thread 的 C
    • CMT（Chip-Multithreading，晶片多執行緒）：每個核心分配多個 hardware thread。Intel 稱為 hyperthreading（超執行緒）。
    • 投影片例子：4 核心、每核 2 個 hardware thread → OS 看到 8 個 logical processor（CPU0–CPU7）。

    兩層排程：

     software threads   ⌇ ⌇ ⌇ ⌇
        level 1：OS 決定哪個 software thread 跑在哪個 hardware thread 上
 hardware threads    ⌇   ⌇     （logical processors）
        level 2：核心決定哪個 hardware thread 使用運算單元
 processing core      [core]
    • 若 OS 知道處理器資源的共享程度，就能把 software thread 排到不共享資源的 logical processor 上。

    補充例子：一個廚師（核心）同時顧兩鍋菜（hardware thread）。一鍋在等水滾（memory stall）時，就去處理另一鍋。從外面看像有兩個廚師，但其實只有一雙手，所以兩個 hardware thread 的效能不等於兩個真正的核心。

    5.5.3 Load Balancing（負載平衡）

    • Load balancing：試著讓 SMP 系統中所有處理器的工作量平均分配，才能充分發揮多處理器的好處。
    • 通常只有在每個處理器各有私有 ready queue 的系統才需要；大多數 OS 採用這種方式。
    • 共用 run queue 的系統通常不需要：處理器一閒下來就立刻從共用佇列取出可執行的 process。
    方法 中文 做法
    Push migration 推送遷移 一個特定的 task 定期檢查各處理器的負載；發現不平衡時，把 process 從過載的處理器推到閒置或較不忙的處理器
    Pull migration 拉取遷移 閒置的處理器從忙碌的處理器拉一個等待中的 task 過來
    • Push 與 pull 通常同時並用。投影片 例：Linux scheduler 與 FreeBSD ULE scheduler。

    5.5.4 Processor Affinity（處理器親和性）

    • Processor affinity（affinity：喜好、傾向）：process 對目前正在執行它的處理器有親和性。
    • 大多數 SMP 系統會盡量讓 process 留在同一個處理器上，以利用該處理器 cache 中已有的資料。

    投影片 投影片圖：記憶體中的資料 X 被載入處理器 A 的 cache。若 process 被搬到處理器 B，B 的 cache 中沒有 X，必須重新載入；A 的 cache 中的 X 也要作廢——這就是遷移的代價。

    類型 中文 說明
    Soft affinity 軟親和性 盡量讓 process 留在同一處理器，但不保證
    Hard affinity 硬親和性 系統提供 system call，讓 process 指定自己只能在哪些處理器上執行
    • 很多系統兩種都提供。投影片 例：Linux 提供 sched_setaffinity() system call 支援 hard affinity。

    補充：Load balancing 和 processor affinity 互相拉扯——為了平衡而搬移 process，就會失去 cache 的好處。

    NUMA 與 CPU 排程：

    • NUMA（Non-Uniform Memory Access） 架構：CPU 存取主記憶體某些部分比其他部分快（回顧 Ch1）。
    • CPU 排程與記憶體配置演算法要一起考慮 affinity。
    • 若 OS 是 NUMA-aware（NUMA 感知），會把記憶體配置在靠近該 thread 所執行 CPU 的地方。

    5.6 即時 CPU 排程 (Real-Time CPU Scheduling)

    即時 OS 的 CPU 排程有一些特殊問題。

    Soft real-time system（軟即時系統） Hard real-time system（硬即時系統）
    保證 不保證關鍵的即時 process 何時被排程；只保證它比非關鍵的 process 優先 工作必須在 deadline 前完成；超過 deadline 才服務，等於沒有服務
    補充例子 影音串流偶爾延遲一下還能接受 汽車安全氣囊、心律調節器

    回顧 Ch1：Real-time 與 embedded system

    • Embedded system（嵌入式系統）：硬體、軟體（可能再加上機械或其他零件）的組合，設計來執行特定工作。嵌入式系統差異相當大，有些有 OS、有些沒有；幾乎都執行 embedded real-time OS。
    • Real-time system：常作為專用應用中的控制裝置；有明確、固定的時間限制；必須在限制時間內回傳正確結果才算運作正確。

    5.6.1 Minimizing Latency（最小化延遲）

    • 即時系統是 event-driven（事件驅動） 的：通常在等某個即時事件發生，一發生就必須盡快回應並服務。
    • Event latency（事件延遲）：從事件發生到被服務所經過的時間。
       event E first occurs                real-time system responds to E
          t0 ◄──────── event latency ────────► t1
   ────────────────────────────────────────────────► Time

    影響效能的兩種延遲重點：

    Interrupt latency（中斷延遲） Dispatch latency（分派延遲）
    定義 從中斷到達 CPU 到開始執行服務該中斷的常式（ISR） 的時間 Scheduler 把目前的 process 移出 CPU 並切換到另一個 所需的時間
    包含 判斷中斷類型 → context switch → 開始 ISR Conflicts 階段 ＋ Dispatch 階段
    要求 即時 OS 應該最小化；硬即時系統必須有上限（bounded） 保持低 dispatch latency 最有效的方法是提供 preemptive kernel

    Dispatch latency 的組成（投影片圖）：

     event                                                    response to event
   │◄───────────────────── response interval ──────────────────────►│
   │◄ interrupt ►│◄────────── dispatch latency ──────────►│◄ real-time ►│
   │ processing  │◄── conflicts ──►│◄──── dispatch ─────►│  process    │
                 ↑                                        │  execution  │
         process made available
    • Conflicts（衝突階段）：(1) 搶占 kernel 中正在執行的任何 process；(2) 讓低優先權 process 釋放高優先權 process 需要的資源。（補充，取自課本對此圖的說明）
    • Dispatch：把高優先權 process 排上可用的 CPU。

    5.6.2 Priority-based Scheduling（以優先權為基礎的排程）

    • 即時排程器必須支援 preemptive、priority-based 排程。
      • 但這只保證 soft real-time。
      • 投影片 例：Linux、Windows、Solaris 都給即時 process 最高優先權。
    • Hard real-time 還必須提供滿足 deadline 的能力。

    Periodic process（週期性行程）的特性：

    • 以固定間隔需要 CPU。
    • 有固定的 processing time t（處理時間）、deadline d（截止期限）、period p（週期）。
    • 0 ≤ t ≤ d ≤ p
    • 週期性工作的 rate（速率） 是 1/p。

    Admission control（准入控制）：

    • Process 可能要向排程器宣告它的 deadline 需求。
    • 排程器用 admission-control algorithm：
      • 接受（admit） 該 process，並保證它能準時完成；或
      • 若無法保證在 deadline 前服務完，就拒絕（reject） 這個請求。

    5.6.3 Rate-Monotonic Scheduling（RMS，速率單調排程）重點

    • 用靜態優先權（static priority） 加上搶占來排程週期性工作。
    • 優先權與週期成反比：
      • 週期越短 → 優先權越高（週期越短的先做；速率越高的先做）
      • 週期越長 → 優先權越低
      • 理由：越常需要 CPU 的工作，給越高的優先權。
    • 假設週期性 process 每次 CPU burst 的處理時間都相同。

    投影片例子 1：P1：p1 = 50、t1 = 20；P2：p2 = 100、t2 = 35

    • Admission control：檢查能否讓這些工作都趕上 deadline。
      • CPU 使用率：P1 = 20/50 = 0.4，P2 = 35/100 = 0.35，總和 0.75。
    • P1 週期較短，P1 的優先權高於 P2。

    （補充：完整排程如下，兩者都趕上 deadline。）

    | P1 |   P2   | P1 |P2|  idle  | P1 |   P2   | P1 |P2| idle |
0   20       50   70 75       100  120     150  170 175    200
Deadlines:      P1(50)    P1,P2(100)      P1(150)    P1,P2(200)

    P2 在 20–50 跑了 30，被 50 到達的 P1 搶占，70–75 跑完剩下的 5，在 deadline 100 之前完成。

    RMS 的限制：

    • RMS 是最佳的（在靜態優先權演算法中），但有一個限制：CPU 使用率有上限，不一定能把 CPU 資源用滿。
    • 排程 N 個 process 的最壞情況 CPU 使用率上限：
    U ≤ N (2^(1/N) − 1)

N = 2 時：2 × (√2 − 1) = 0.828…，約 83%

    投影片例子 2：RMS 錯過 deadline——P1：p1 = 50、t1 = 25；P2：p2 = 80、t2 = 35

    • 使用率 = 25/50 + 35/80 = 0.5 + 0.4375 ≈ 94%，超過 83% 的上限。
    |   P1   |   P2   |   P1   |P2|
0       25       50       75 80  ← P2 的 deadline 80 到了，卻只做了 25 + 5 = 30，還差 5
    • P1 優先權較高，0–25 先跑；P2 跑 25–50 後被 50 到達的 P1 搶占；P1 跑到 75；P2 只剩 75–80 這 5 ms，來不及在 80 之前完成 35。

    補充：使用率超過上限不代表一定會錯過 deadline，只是 RMS 不再保證；低於上限則保證一定排得出來。

    5.6.4 Earliest-Deadline-First Scheduling（EDF，最早截止期限優先）重點

    • Process 變成可執行時，向排程器宣告它的 deadline。
    • 動態（dynamically） 依 deadline 指定優先權：
      • deadline 越早 → 優先權越高
      • deadline 越晚 → 優先權越低

    投影片例子：同一組 P1：p1 = 50、t1 = 25；P2：p2 = 80、t2 = 35（RMS 排不出來的那組）

    |  P1  |    P2    |  P1  | P2 |  P1  | P2 |   | P1 ...
0     25         60     85  100   125  145  150
    • 0–25：P1（deadline 50）先跑完。
    • 25：只剩 P2（deadline 80）。50 時 P1 的第二期到達，deadline 是 100，比 P2 的 80 晚，所以 P2 不被搶占，一路跑到 60 完成。
    • 60–85：P1（deadline 100）。80 時 P2 的第二期到達，deadline 160，比 P1 的 100 晚，不搶占。
    • 85–100：P2。100 時 P1 第三期到達，deadline 150 早於 P2 的 160 → P1 搶占。
    • 100–125：P1；125–145：P2 做完剩下的 20；145–150 閒置；150 起 P1……
    • 所有 deadline 都趕上了。

    EDF 的特點：

    • 與 RMS 不同，EDF 不要求 process 是週期性的，也不要求每次 burst 的 CPU 時間固定。
    • EDF 理論上是最佳的：能讓每個 process 都趕上 deadline，且 CPU 使用率可達 100%。
    • 實際上不可能達到 100%：process 之間的 context switch 與中斷處理都有成本。

    5.6.5 Proportional Share Scheduling（比例分配排程）

    • 把 T 份（shares） 分配給所有應用程式。
    • 一個應用程式拿到 N 份，就保證它得到總處理器時間的 N / T（N < T）。
    • 投影片 例：T = 100 份——A 拿 50 份、B 拿 15 份、C 拿 20 份 → A 得到 50%、B 15%、C 20% 的處理器時間。
    • 必須搭配 admission-control policy：只有在剩下的份數足夠時，才接受要求特定份數的 client。

    5.6.6 POSIX Real-Time Scheduling

    • 依據 POSIX.1b 標準；POSIX API 提供排程即時 thread 的相關函式。
    • 為即時 thread 定義兩種排程類別：
    類別 說明
    SCHED_FIFO 用 FIFO 佇列，以 FCFS 排程；相同優先權的 thread 之間沒有 time-slicing
    SCHED_RR 和 SCHED_FIFO 類似，但相同優先權的 thread 之間會 time-slicing（輪流）

    （另外還有 SCHED_OTHER，由系統自行定義，非即時。）

    • 取得與設定排程策略的兩個函式：
      • pthread_attr_getschedpolicy(pthread_attr_t *attr, int *policy)
      • pthread_attr_setschedpolicy(pthread_attr_t *attr, int policy)

    投影片例子（Fig. 5.25）：POSIX real-time scheduling API

    #include <pthread.h>
#include <stdio.h>
#define NUM_THREADS 5

int main(int argc, char *argv[])
{
    int i, policy;
    pthread_t tid[NUM_THREADS];
    pthread_attr_t attr;

    /* get the default attributes */
    pthread_attr_init(&attr);

    /* get the current scheduling policy */
    if (pthread_attr_getschedpolicy(&attr, &policy) != 0)
        fprintf(stderr, "Unable to get policy.\n");
    else {
        if (policy == SCHED_OTHER) printf("SCHED_OTHER\n");
        else if (policy == SCHED_RR) printf("SCHED_RR\n");
        else if (policy == SCHED_FIFO) printf("SCHED_FIFO\n");
    }

    /* set the scheduling policy - FIFO, RR, or OTHER */
    if (pthread_attr_setschedpolicy(&attr, SCHED_FIFO) != 0)
        fprintf(stderr, "Unable to set policy.\n");

    /* create the threads */
    for (i = 0; i < NUM_THREADS; i++)
        pthread_create(&tid[i], &attr, runner, NULL);

    /* now join on each thread */
    for (i = 0; i < NUM_THREADS; i++)
        pthread_join(tid[i], NULL);
}

/* Each thread will begin control in this function */
void *runner(void *param)
{
    /* do some work ... */
    pthread_exit(0);
}

    留意 投影片第 89 頁把函式名稱寫成 pthread_attr_getsched _policy（多了空格、多了底線），正確名稱是程式碼中的 pthread_attr_getschedpolicy；pthread exit 也應為 pthread_exit。

    版本 2.5 之前與 2.5：O(1) scheduler

    • 2.5 之前：使用標準 UNIX 排程演算法的變形。
    • 2.5 版改成常數時間 O(1) 的排程：
      • Preemptive、priority-based
      • 兩個優先權範圍：time-sharing 與 real-time
      • Real-time 範圍 0–99，nice value 對應 100–140

    版本 2.6.23 之後：CFS重點

    CFS（Completely Fair Scheduler，完全公平排程器）：

    • Scheduling class（排程類別）：
      • 每個類別有特定的優先權。
      • 排程器選擇最高優先權類別中、優先權最高的 task。
      • 不再用固定長度的 quantum，而是依 CPU 時間的比例分配。
      • 內建 2 個類別，可以再加：(1) default、(2) real-time。
    • 依 nice value（−20 到 +19） 計算 quantum：
      • 數值越低，優先權越高。
      • 計算 target latency（目標延遲）：每個 task 至少應該執行一次的時間間隔。
      • Active task 數量增加時，target latency 可能變大。
    • CFS 為每個 task 維護一個 virtual run time（虛擬執行時間），存在變數 vruntime：
      • 依 task 的優先權有一個 decay factor（衰減係數）：優先權越低，衰減率越高（vruntime 增加得越快）。
      • 預設（normal）優先權的 task：virtual run time ＝ 實際執行時間。
    • 選擇 vruntime 最小的 task 作為下一個執行者。

    投影片例子：CFS 的效能

    • 每個可執行的 task 放在一棵 red-black tree（紅黑樹） 中——一種平衡二元搜尋樹，key 是 vruntime。
    • Task 變成可執行時加入樹；不可執行時（例如在等 I/O）從樹中移除。
    • 拿到較少處理時間的 task（vruntime 較小）在樹的左邊；拿到較多的在右邊。
    • 最左邊的節點 vruntime 最小，就是優先權最高的 task。
    • 樹是平衡的，找最左節點需要 O(lg N)；但 Linux 把這個值快取在變數 rb_leftmost，所以決定下一個 task 只需要讀取快取值。

    補充例子：CFS 像輪流玩遊戲機，誰玩得最少誰下一個玩。優先權高的人，計時器走得比較慢，所以能玩比較久。

    Real-time 與全域優先權：

    • Real-time 排程依照 POSIX.1b；real-time task 有靜態優先權。
    • Real-time 加上一般 task 對應到同一套全域優先權：
     0 ──────────── 99 | 100 ──────────── 139
     real-time      |       normal
 數字越小 → 優先權越高
 nice −20 → 100        nice +19 → 139

    Linux 的負載平衡與 NUMA：

    • Linux 支援 load balancing，同時也是 NUMA-aware。
    • Scheduling domain（排程網域）：一組可以互相平衡負載的 CPU 核心。
    • 網域依照共享的資源（例如 cache）來組織。目標是避免 thread 在網域之間遷移。

    投影片例子：一個 physical processor domain（NUMA node）下有 domain0（core0、core1 共用一個 L2）與 domain1（core2、core3 共用一個 L2），四個核心共用 L3。Thread 盡量在同一個 domain 內移動，才不會失去 L2 cache 中的資料。

    5.7.2 Windows Scheduling

    • Windows 使用 priority-based preemptive scheduling（以優先權為基礎的可搶占排程）。
    • 優先權最高的 thread 下一個執行。
    • Dispatcher 就是 scheduler。
    • Thread 一直執行，直到：(1) block、(2) 用完 time slice、(3) 被更高優先權的 thread 搶占、(4) 終止。
    • Real-time thread 可以搶占非 real-time thread。
    • 32 級優先權：
      • Variable class（可變類別）：1–15
      • Real-time class（即時類別）：16–31
      • 優先權 0：memory-management thread
    • 每個優先權一個佇列。
    • 沒有可執行的 thread 時，執行 idle thread。

    Windows 優先權類別（priority class）與相對優先權（relative priority）：

    • Win32 API 定義 process 可屬於的幾種 priority class： REALTIME_PRIORITY_CLASS、HIGH_PRIORITY_CLASS、ABOVE_NORMAL_PRIORITY_CLASS、NORMAL_PRIORITY_CLASS、BELOW_NORMAL_PRIORITY_CLASS、IDLE_PRIORITY_CLASS
      • 除了 REALTIME 之外都是 variable（可變的）。
    • 某個 priority class 內的 thread 有一個 relative priority： TIME_CRITICAL、HIGHEST、ABOVE_NORMAL、NORMAL、BELOW_NORMAL、LOWEST、IDLE
    • Priority class ＋ relative priority → 數字優先權：

    優先權的動態調整：

    • Base priority（基礎優先權） 是該 class 中的 NORMAL 那一格（表中粗體）。
    • Quantum 用完 → 優先權降低，但絕不低於 base。
    • 發生等待（wait） 後 → 依等待的對象提高（boost） 優先權（例如等鍵盤輸入的 boost 比等磁碟的大）。
    • 前景視窗（foreground window） 的 quantum 給 3 倍的加成（3x priority boost）。

    • Windows 7 加入 UMS（User-Mode Scheduling，使用者模式排程）：
      • 應用程式獨立於 kernel 建立與管理 thread。
      • 對大量 thread 而言有效率得多。
      • UMS 排程器來自程式語言函式庫，例如 C++ Concurrent Runtime（ConcRT） framework。

    5.8 演算法評估 (Algorithm Evaluation)

    選擇 CPU 排程演算法的準則可能結合多項量測，例如：

    • 在最大回應時間 300 ms 的限制下，最大化 CPU 使用率。
    • 最大化 throughput，使 turnaround time（平均而言）與總執行時間成線性比例。

    四種評估方法：

    方法 中文 一句話
    Deterministic modeling 決定性模型 拿一組固定的工作負載，算出每個演算法的表現
    Queueing models 佇列模型 用機率分布與數學公式分析
    Simulations 模擬 寫程式模擬電腦系統
    Implementation 實作 直接寫進 OS 實際跑

    5.8.1 Deterministic Modeling（決定性模型）

    （deterministic：既定性的、決定性的）

    • 拿一組特定、預先決定好的工作負載，定義每個演算法在這組負載下的效能。
    • 優點：簡單、快速；給出確切的數字，可以直接比較演算法。
    • 缺點：需要確切的輸入數字，答案也只適用於這些情況；太特定，需要太多確切的知識才有用。
    • 主要用途：描述排程演算法與提供範例（本章的例子都是這種）。

    投影片例子：5 個 process，全部在時間 0 到達

    P1 10
    P2 29
    P3 3
    P4 7
    P5 12

    5.8.2 Queueing Models（佇列模型）

    • 很多系統上執行的 process 每天都不同，沒有一組固定的 process（與時間）能用於 deterministic modeling。
    • 可以決定的是：
      • CPU 與 I/O burst 的分布：描述某個 CPU burst 出現機率的數學公式，通常是 exponential（指數）分布，用平均值（mean） 描述。
      • Process 到達時間的分布。
    • 這些分布可以實際量測後近似，或直接估計。

    Modeling computer system（電腦系統的建模）：

    • 把電腦系統描述成一個 network of servers（伺服器網路）。
      • 每個 server 有一個等待中的 process 佇列。
      • CPU 是一個 server，它的佇列是 ready queue；I/O 系統也是，它的佇列是 device queue。
    • Queueing-network analysis（佇列網路分析）：
      • 已知：arrival rate（到達率）與 service rate（服務率）
      • 計算：使用率、平均佇列長度、平均等待時間等

    Little's formula（Little 公式）重點：

    n = λ × W
    符號 意義
    n 平均佇列長度（不含正在被服務的 process）
    W 佇列中的平均等待時間
    λ 新 process 的平均到達率
    • 成立條件：系統處於穩態（steady state），即 process 到達率 = process 離開率。
    • 知道其中兩個就能算出第三個。

    補充例子：平均每秒到達 7 個 process（λ = 7），佇列中平均有 14 個 process（n = 14），則平均等待時間 W = n / λ = 14 / 7 = 2 秒。

    補充比喻：一家拉麵店每分鐘來 2 位客人，每位平均要在門口排 10 分鐘，那門口平均就有 2 × 10 = 20 人在排隊。

    • 用來比較排程演算法很有用，但有限制：到達與服務的分布常被定義成不切實際、但數學上容易處理（tractable） 的形式。

    5.8.3 Simulations（模擬）

    • 模擬能對排程演算法做更準確的評估。
    • 用軟體寫出電腦系統的模型：
      • Simulator（模擬器）：有一個代表時鐘（clock） 的變數；時鐘增加時，模擬器修改系統狀態，反映裝置、process 與排程器的活動。
      • Input data（輸入資料）
      • Output of statistics（統計輸出）

    投影片例子：模擬器的結構

    輸入：每筆紀錄包含 pid、arrive-time、burst-time、priority

    模擬器（虛擬碼）：

    clock = 0
While not-end-of-input-records
{
    if clock == r.arrive-time
        RunPolicy        // preemptive
    if clock == r.finish-time
        RunPolicy        // non-preemptive
                         // preemptive
    clock++;
    ....
}

    每個排程物件：

    Class schedule
{
    checkinthread();
    checkoutthread();
}

    輸出：Gantt chart、平均等待時間、平均 turnaround time、context switch 次數、完成所有 process 所需的總時間

    說明：nonpreemptive 演算法只在有 process 完成時才需要重新決策；preemptive 演算法在有 process 到達時也要重新決策（看新來的是否應該搶占）。

    5.8.4 Implementation（實作）

    • 評估排程演算法唯一完全準確的方法：把它寫進 OS，看它實際運作得如何。
    • 讓真正的演算法在真實系統、真實運作條件下接受評估。
    • 主要困難：成本很高（要修改 OS、測試，還要觀察使用者的反應；使用者也可能改變行為來配合新排程器）。

    投影片例子：NCNU IM OS Simulator——http://ossim.im.ncnu.edu.tw/ 暨大資管系的作業系統線上模擬器（Operating System Online Simulator），可模擬 CPU Scheduling、Real-Time Scheduling、Deadlock、Page Replacement、Disk Scheduling，可以註冊帳號或以訪客身分使用。本章作業的「實驗組」會用到它。

    四種評估方法比較

    方法 準確度 成本 特點
    Deterministic modeling 只對特定輸入準確 最低 簡單快速，適合教學範例
    Queueing models 取決於分布是否貼近現實 低 數學分析，但假設常不切實際
    Simulations 較準確 中到高 可用 trace tape 重現真實負載
    Implementation 完全準確 最高 真實環境測試

    排程演算法總表

    演算法 選誰 可搶占？ 優點 缺點

    計算題 SOP（補充整理）

    1. 依到達時間與規則畫出 Gantt chart。
      • Nonpreemptive：只在有 process 完成時重新選。
      • Preemptive：有 process 到達時也要重新比較。
    2. 從 Gantt chart 讀出每個 process 的 completion time。
    3. Turnaround = Completion − Arrival
    4. Waiting = Turnaround − Burst
    5. 平均等待時間 = 所有 waiting 的總和 ÷ process 數。

    容易混淆的觀念對照

    比較 A B
    CPU scheduler vs. Dispatcher 決定下一個執行誰 執行切換（context switch、切回 user mode、跳到程式位置）
    Preemptive vs. Nonpreemptive 在 4 種情況（甚至 5 種）都可能排程，可以把執行中的 process 換掉 只在 running → waiting 與 terminate 時排程
    I/O-bound vs. CPU-bound 很多短的 CPU burst 少數長的 CPU burst
    Turnaround vs. Waiting vs. Response time 送出到完成 在 ready queue 等的總時間
    SJF vs. SRTF 不可搶占；一次跑完整個 burst 可搶占；比的是剩餘時間
    External vs. Internal priority 外部因素（重要性、付費） 可量測的數值（時間限制、記憶體需求）
    Starvation vs. Aging 問題：低優先權永遠等不到 解法：等越久優先權越高
    Multilevel queue vs. MLFQ Process 永久固定在一個佇列 Process 可依行為升降級
    Fixed-priority vs. Time slice among queues 高優先權佇列空了才輪到低的 依比例分配 CPU 時間（如 80% / 20%）
    PCS vs. SCS Thread library 排程；同 process 內競爭 Kernel 排程；全系統競爭
    Asymmetric vs. Symmetric multiprocessing 一個 master 處理系統活動 每個處理器自己排程
    Homogeneous vs. Heterogeneous 處理器功能相同 處理器能力不同
    Common vs. Private ready queue 不需 load balancing，但有存取衝突 需要 load balancing，cache 利用較好
    Push vs. Pull migration 定期檢查，把工作從忙的推給閒的 閒的處理器自己去拉工作
    Soft vs. Hard affinity 盡量留在同一處理器，不保證 用 system call 指定只能在哪些處理器上跑
    Physical core vs. Logical processor 實體運算單元 每個 hardware thread 對 OS 都是一個 logical processor
    Soft vs. Hard real-time 只保證優先於非關鍵 process 必須在 deadline 前完成
    Interrupt latency vs. Dispatch latency 中斷到達 → ISR 開始 停止一個 process → 開始另一個
    RMS vs. EDF 靜態優先權，週期越短越高 動態優先權，deadline 越早越高
    SCHED_FIFO vs. SCHED_RR 同優先權不輪流 同優先權用 time-slicing 輪流
    O(1) scheduler vs. CFS Linux 2.5：active／expired 兩個 array Linux 2.6.23+：依 vruntime，紅黑樹
    Linux nice vs. Windows priority 數字越小優先權越高 數字越大優先權越高
    Distribution-driven vs. Trace tape 隨機產生資料 用真實系統的紀錄
